# Автоматическая редакция MetricHit: матрица публикации

Дата проверки официальных источников: 2026-08-13
Режим исследования: read-only, без входа в аккаунты

## Обозначения

- `automatic` — официальный API позволяет отправить и подтвердить публикацию; всё равно нужен approval владельца.
- `draft-only` — система готовит и согласует payload, но не изменяет площадку.
- `manual-package` — Markdown/HTML/assets/checklist передаются владельцу для ручной работы.
- `unsupported` — не входит в редакционный конвейер.

Отсутствие найденной документации не доказывает отсутствие внутреннего API. До официального подтверждения применяется более безопасный режим.

## Telegram

Подтверждённые официальные возможности:

- [Telegram Bot API](https://core.telegram.org/bots/api) — `sendMessage`, `sendPhoto`, `sendDocument`, inline keyboards, callback query, входящие voice и возврат объекта `Message`;
- username канала можно передать как `chat_id`; для публикации бот должен быть администратором с нужным правом;
- обычный Bot API не документирует `schedule_date` для `sendMessage`, поэтому MVP хранит расписание сам и вызывает API в нужный момент;
- [полная статистика канала](https://core.telegram.org/method/stats.getBroadcastStats) доступна через MTProto только пользователям-администраторам и зависит от `can_view_stats`. Использовать пользовательскую сессию в MVP не рекомендуется.

Риски и условия:

- Bot API token — только во внешнем secret store;
- target фиксируется числовым chat ID и ожидаемым публичным username;
- перед включением — тест в отдельном тестовом канале, затем один контролируемый пост;
- отправленное сообщение нельзя считать опубликованным без сверки returned message ID и доступности URL;
- Telegram-бот для согласований одновременно проверяет allowlisted numeric `user_id`, ожидаемый `chat_id` и `chat.type=private`.

Режим: `automatic` для канала после каждого отдельного owner approval. Аналитика в MVP: доступные публичные counters/ручной snapshot, без userbot.

Bot API не документирует idempotency key и надёжный поиск сообщения, ответ на отправку которого потерян. Поэтому timeout после возможной передачи `sendMessage`/media переводит задание в `publish_uncertain`: автоматического повтора нет. Владелец сверяет канал и привязывает message ID/URL либо выдаёт новое разрешение на осознанную повторную отправку.

## VK

Официальный источник — репозиторий схем [VKCOM/vk-api-schema](https://github.com/VKCOM/vk-api-schema):

- [`wall.post`](https://github.com/VKCOM/vk-api-schema/blob/master/wall/methods.json) создаёт пост и прямо описан как способ публикации suggested/scheduled posts; параметр `publish_date` присутствует;
- `wall.getById` возвращает посты по ID;
- [`stats.get` и `stats.getPostReach`](https://github.com/VKCOM/vk-api-schema/blob/master/stats/methods.json) возвращают статистику сообщества и reach поста;
- [`photos.getWallUploadServer`/`photos.saveWallPhoto`](https://github.com/VKCOM/vk-api-schema/blob/master/photos/methods.json) задают штатный upload flow.

Существенный риск: текущая официальная schema 5.199 указывает user access token для `wall.post`, `stats.get` и upload-методов. Это более широкая и чувствительная авторизация, чем токен одного бота. До практического capability test нельзя обещать безопасную публикацию изображений токеном сообщества.

Режим: `draft-only` в первом включении. Перевод в `automatic` возможен после решения владельца, документированного минимального scope, тестовой группы, публикации/сверки/удаления тестового поста вручную владельцем и проверки recovery. Удаление реальных постов автоматически не включать.

## Дзен

Официальная [Справка Дзена](https://dzen.ru/help/) не открылась read-only инструментом, а публичная официальная документация API для создания авторских статей не была найдена. Это фиксируется как недостаток доказательств, а не как утверждение «API не существует».

Существующие три URL подтверждают использование площадки MetricHit, но не интерфейс автоматизации. Не применять cookie/session automation и не строить browser automation как основной путь.

Пакет должен содержать:

- `article.md` и `preview.html`;
- title, lead, рубрику/теги как рекомендации;
- обложку и proof-of-rights;
- источники и checklist ручной проверки;
- ожидаемый canonical URL field;
- короткие производные посты отдельно, без копирования статьи.

Режим: `manual-package`. После размещения владелец передаёт URL; только после проверки запись становится `published_confirmed`.

## Sostav/SBlogs

[Правила SBlogs](https://www.sostav.ru/blogs/policy/blog) подтверждают пользовательские и корпоративные блоги, изображения/видео с правами и модерацию. Для MetricHit особенно важны:

- ссылки на свои проекты допустимы в контексте экспертизы, но чистая реклама запрещена вне соответствующих блогов;
- материалы на разных площадках не должны дублироваться;
- желательный объём 3–9 тыс. знаков;
- UTM, referral и сокращённые ссылки запрещены;
- непроверенные источники и вводящие в заблуждение заголовки блокируются;
- изображения с ярким логотипом/текстом могут быть убраны из ленты.

Публичной официальной документации API, draft, scheduling и programmatic stats не найдено. Режим: `manual-package`; пакетный checklist обязан запрещать UTM и проверять оригинальность версии.

## Oborot.ru

[Правила Oborot.ru](https://oborot.ru/p/community-rules-i31029.html) описывают создание блога через `Сообщества → Блоги`, требуют структурированный оригинальный материал и права на media. Реклама трактуется широко: контакты, акции, логотипы и предложения услуг могут быть признаны рекламой. Кросс-посты не следует использовать как основу блога. Публикуя материал, автор предоставляет площадке широкую неисключительную лицензию — это требует осознанного ручного решения.

Отдельная [страница рекламного размещения](https://oborot.ru/p/reklama-na-sajte-i30677.html) подтверждает редакционное согласование платных материалов. Бесплатный блог и рекламная статья — разные маршруты; оркестратор не должен выбирать между ними или создавать расходы.

Режим: `manual-package`, пока создание блога и допустимый формат MetricHit не подтверждены. CTA и коммерческие ссылки проверяет владелец.

## Timeweb Cloud

Официальное приглашение [авторам Timeweb Cloud](https://timeweb.cloud/blog/pishi-pomogaj-poluchaj-dengi-prihodite-k-nam-pisat-gajdy-po-devopsu-i-razrabotke) описывает редакционный процесс: согласование темы и условий, ТЗ, написание, редакторская и техническая проверка, доработка, публикация редакцией. Статья должна быть уникальной, опираться на реальный опыт и быть полезной аудитории.

Это не self-service publishing API. Тема MetricHit должна быть принята редакцией и соответствовать IT-аудитории; отправленный питч не означает доступ к публикации.

Режим: `manual-package`. Пакет формируется только после ответа редакции и включает их актуальное ТЗ.

## Workspace

[Официальная инструкция Workspace Media](https://workspace.ru/blog/how-to-publish-your-article/) подтверждает self-service публикацию через личный кабинет, сохранение материала, добавление иллюстраций и постмодерацию. После нажатия «Опубликовать» материал появляется в ленте; штатное API или scheduling в инструкции не описаны.

Режим: `manual-package`. Это сильный кандидат для коммерческого семантического кластера, но решение о площадке, профиле автора и теме принимает владелец.

## MAX и Avito

MAX включён только потому, что упомянут в импортированных материалах. Официальные методы [`POST /messages`](https://dev.max.ru/docs-api/methods/POST/messages) и [`POST /uploads`](https://dev.max.ru/docs-api/methods/POST/uploads) позволяют боту отправлять текст/media в канал; объект [`Message`](https://dev.max.ru/docs-api/objects/Message) содержит публичный URL и статистику канального поста. Технически будущий `automatic` возможен, но без подтверждённого канала и редакционного решения добавлять его в MVP нельзя.

Avito — сервис объявлений, а не площадка полноформатной редакции в текущей стратегии. Этап закрыт владельцем; режим `unsupported`.

## Проверка перед включением любого automatic-адаптера

1. официальный метод и его текущие scopes повторно проверены;
2. target/account однозначно подтверждён владельцем;
3. secret store и ACL исправлены;
4. токен имеет минимальные права и не попадает в Git/log/backup;
5. simulation и контрактные тесты проходят;
6. тест выполнен в отдельном тестовом target;
7. проверены media, URL, reconciliation и защита от дубля;
8. владелец разрешил production target отдельным решением;
9. kill switch и ручное восстановление проверены;
10. правила площадки и юридическая допустимость перепроверены на дату запуска.
