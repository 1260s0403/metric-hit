# Operating context «Ядра»

> Правило быстрой поставки: 5 минут для fast path и 10 минут для standard — цель законченного полезного этапа и предел служебной подготовки, а не цикл повторных owner confirmations. In-scope разрешение непрерывно действует до result/blocker. Объективно более длинная работа заранее делится на независимо полезные этапы, но не прерывается каждые 5 минут ради формального согласования. Потенциально долгие неинтерактивные команды запускаются через `node scripts/command-deadline.mjs <секунды> -- <команда>`, а timeout останавливает этап без второго executor-а.

Исполнение идёт только в объявленном векторе: один проверяемый результат и точные необходимые files/resources. Strategy остаётся read-only human-facing router и передаёт этот scope одному executor-у; sibling и unrelated files/resources нельзя читать или менять без доказанной прямой зависимости. Executor использует только существующие workflow и не создаёт неуказанные механизмы. Любая попутная проблема отражается в итоговом отчёте как observation/blocker, но не исправляется «заодно»; если без неё результат невозможен, executor останавливается с точным blocker без автоматического расширения scope. Поставка — только проверенный результат с чистым Git либо точный технический blocker.

## Обязательный startup protocol

Новый Strategy-чат читает `AGENTS.md`, `knowledge/approved/current-context.md`, этот документ и `documents/roadmap.md`; затем проверяет branch, HEAD, `git status --short`, `work/inbox/` и релевантную approved memory read-only. Конкретная задача загружает только parent chain, применимые правила и необходимые для объявленного вектора файлы; полный startup не повторяется для простой задачи и не запускается только из-за слов `architecture`, `policy` или `governance` в формулировке. Перед изменением operator panel обязательно читается `documents/operator-panel-ux-contract.md`.

Точная фраза владельца «Ядро старт» без suffix в новом Strategy-чате запускает read-only startup: прочитать current context, operating context и roadmap; проверить branch, HEAD, status, `work/inbox/` и релевантную approved memory. Если current context указывает рабочий local URL, проверить его GET-запросом без рестарта runtime. В рамках команды запрещены изменения файлов, БД, памяти, configuration и Git, запуск executor-а, restart runtime и создание user/sidebar-задач. После проверки Strategy кратко сообщает фактическое состояние, актуальный приоритет, ближайший шаг и противоречия, незавершённые обязательства или blocker, затем остаётся read-only до явного in-scope запроса владельца.

Scoped-команда `Ядро старт. <контур>.` в новом рабочем чате является startup activation. До любого status и до принятия задачи executor обязан выполнить подходящую уже существующую repo-side preparation: `chat-workspace-prepare` для active named scope или resume, `chat-parallel-start` для точной новой project-task или named Telegram-бота. Он проверяет фактические noncanonical branch, абсолютный worktree, HEAD и clean state и только затем сообщает status с branch и абсолютным путём. При любой ошибке preparation, legacy checkpoint или drift он сообщает точный blocker; запрещены fallback к канонической ветке `codex/telegram-bot` и подмена Git worktree логической папкой `work/`. Это не создаёт и не привязывает UI-чат к worktree через Codex API/daemon: activation выполняется как обязательная часть обычного запуска инструкции.

## Execution card и проверка поставки

До начала любой editorial, code, docs/research, UI, governance или иной задачи Strategy определяет scope и type, после чего существующий compiler `scripts/structured-memory.mjs` обязан создать execution card в том же context pack. Без полной card исполнение запрещено и fail-closed отклоняется. Card содержит:

1. один проверяемый результат;
2. точные разрешённые области scope;
3. применимые запреты и требования из `AGENTS.md` и выбранной родительской цепочки памяти;
4. одну существующую первую проверку из карты ниже;
5. измеримые acceptance-критерии;
6. точный перечень запрещённых изменений.

Context pack, execution card и preflight — компактный control plane, а не аудит всей системы. Они не добавляют файлы, resources, проверки или обязательства за пределами результата и parent chain. Служебная подготовка не меняет риск-класс и не расширяет scope; найденная в ней попутная проблема подчиняется тому же правилу observation/blocker без side quest.

Для editorial-задачи compiler дополнительно включает все применимые approved editorial rules и точные owner obligations, даже если они ещё не представлены в `scoped_memory_records`. Выбор ограничен editorial scope/type/platform, не включает unrelated open tasks или sibling rules. Каждый новый публичный пост или статья вне Telegram требует в card один не-навигационный кластер утверждённого ядра либо несколько документированно смежных кластеров, основной запрос, интент, площадку и формат; при нескольких кластерах обязательны полный список и обоснование смежности, а delivery fail-closed проверяет естественное заметное размещение основного запроса, те же кластеры, единый интент и спрос для геокандидата. Для текста 1 800–2 800 знаков обязательны 8–12 уникальных точных целевых запросов, для 2 801–5 000 — 10–16, для 5 001–7 000 — 14–20, для 7 001–9 000 — 18–26; основной входит в количество, каждый вторичный естественно встречается в основном тексте, а текст вне этих диапазонов требует в delivery QA обоснование количества без выдумывания новых порогов. Для таких материалов главная редакционная цель — индексация Яндекса по выбранной семантике; card фиксирует только эту SEO-цель. Свежий материал не проверяется и не обязан быть индексирован до публикации: execution card и delivery QA не требуют индексируемость, находимость, URL, статус или evidence индексации. Только после независимой проверки индексации опубликованный материал может стать кандидатом отдельной ПФ-кампании, которая по-прежнему требует owner approval для конкретного материала/URL, бюджета и scope. Telegram полностью исключён из semantic, indexation и PF-target requirements. Для article/TenChat дополнительно обязательны применимые правила ссылок, H1/ВЧ-запроса, объёма, originality/source overlap и link-spam. Полный fail-closed контракт находится в `documents/structured-memory.md`.

Перед поставкой executor валидирует результат по сохранённой card: подтверждает соблюдение scope, выполнение той же первой проверки и каждого acceptance-критерия и отсутствие запрещённых изменений. Для editorial delivery сохраняются точные результаты реально выполненных deterministic local content checks; originality содержит hashes материала и источников и source-overlap report. Недоступные внешние plagiarism/AI detectors отмечаются только как `unavailable` или `not_performed`, без ложного результата. Успешный `close` обязан записать `terminal_outcome=delivered`. Осиротевший или отменённый пакет закрывается только отдельной audited abandon-операцией с причиной и владельцем, получает `terminal_outcome=abandoned` и не считается поставкой; replay такой операции не создаёт новый audit. Это обязательно для всех типов задач.

Для крупного repair целостности до первой data/schema/filesystem-мутации обязателен полный backup текущего состояния и успешный штатный restore-test. Живая SQLite снимается online; вычисление hash backup-источника допускает совместное чтение с работающим runtime. После проверок и implementation commit создаётся новый полный backup и снова выполняется restore-test. Ошибочный staging-набор не объявляется backup и не удаляется вручную в обход штатного lifecycle.

## Назначение

«Ядро» — OS и управляющий контур для нескольких независимых проектов. Оно связывает информацию, утверждённую память, решения, проекты, задачи, выполнение и аудит. Система не позиционируется как редакционная платформа или замена Notion/Trello. MetricHit — первый проект внутри «Ядра». Понятие «MetricHit OS» не используется для целевой модели.

## Границы ядра

«Ядро» — OS и управляющий контур; MetricHit — первый независимый проект внутри него, а в перспективе проектов может быть несколько. Каждый проект имеет собственные память, правила и бизнес-истину, независимые от «Ядра» и других проектов. Техническое разделение завершено на `acff1db909c9cf9b7b85f0c2a18b035f3d3fa2c0`: любой зарегистрированный managed project маршрутизируется по canonical `project_id` в собственный `data/projects/<project_id>/project.sqlite`, а центральная SQLite остаётся control plane. Некорректные, неизвестные, незарегистрированные проекты и проекты без хранилища отклоняются fail-closed; federated/project store и memory routing поддерживают N проектов, совместимость MetricHit сохранена. Два временных проекта подтвердили изоляцию и export/import; реальный второй проект не создавался. Проверки: Python 196 passed, 1 skipped; Node 63/63; integrity и foreign keys valid; readiness unresolved=0, ready=true. Следующий продуктовый шаг нужен только при появлении реального второго проекта или по отдельному решению о UI; cleanup legacy-копий — только по отдельному решению владельца. Текущая реализация — локальный модульный монолит на Python 3.13, FastAPI и SQLite; Node.js остаётся эталоном совместимости до отдельного решения о завершении миграции.

## Контур решений

Запрос владельца изменить или построить в названном scope является standing authorization на in-scope реализацию, тесты, обычный staging и один commit и считается явным утверждением для workflow. Повторное промежуточное подтверждение не требуется. Strategy делает только то, о чём попросил владелец, и не делает того, о чём владелец не просил; если до выполнения scope, approval или требуемый результат неясен, он не додумывает, а уточняет у владельца. Исключения: удаление, force-операции, внешняя публикация, расходы, изменения доступов/прав, стратегии, политики памяти, настроек/глобальной системы и существенное расширение scope. Managed-sandbox prompts неустранимы и сообщаются только при возникновении.

В общении с владельцем Strategy и исполнитель пишут простым, понятным языком. Внутренние названия Codex, Git, платформы и процесса, а также непонятные сокращения не используются, если владелец сам не просит технические детали. Если возникло важное техническое препятствие, сначала объясняется его смысл обычными словами; точные технические детали добавляются только по просьбе владельца. Итог работы начинается с результата и остаётся кратким.

Контур решений — часть центрального ядра, а не отдел или автономный агент. Только явно утверждённые владельцем решения могут быть approved; предложения и непринятые варианты остаются pending candidates и никогда не auto-approve. Перед сохранением проверяются semantic duplicate, evolution и conflicts. Значимые approved-решения входят в current context; технические мелкие правки решениями не считаются.

Канонический workflow engineering: прямой `Strategy → internal native Codex task-thread/subagent → commit/result` либо утверждённый `Strategy → temporary department coordinator → worker → commit/result`. Strategy — основной human-language координатор продукта, архитектуры, приоритетов и разработки: до решений он сверяет approved memory, current context, operating context, roadmap и фактический Git, отмечает существенные пробелы и противоречия и предлагает ближайшие MVP-шаги. Он не требует повторять известный контекст и не считает историю чата канонической истиной. Strategy остаётся единственным постоянным видимым проектным чатом и read-only потоком. User-owned/sidebar-чаты и `create_thread` не используются. Для одного change set остаются один writer, одна ветка и один commit; завершённый или заблокированный executor не переиспользуется. Controlled parallel execution v1 разрешает максимум четыре активных writer thread только при непересекающихся leases в разных worktree; поэтому один активный engineering thread не блокирует остальные три автоматически, но пятый, конфликт ресурсов или exclusive resource блокируются fail-closed. Пока executor активен, Strategy удерживает пользовательский work turn открытым; финальный итог даётся только после commit/result и clean Git либо при реальном blocker. Repo-side handoff хранит решение, context, lifecycle, evidence и leases. UI, daemon, scheduler, OpenAI API и интеграция внутреннего API Codex не реализуются.

Утверждённые изменения маршрутизируются по фактическому изменению и проверяются минимально достаточно. Fast path — до трёх изменённых tracked-файлов без новых files/dependencies/runtime/config/system/schema/migration: одна существующая целевая проверка, если для контура она есть, и `git diff --check`; для docs-only отдельная специальная проверка не требуется. Standard ограничен одним модулем и запускает только его тесты; E2E обязателен лишь когда менялся соответствующий UI или пользовательский сценарий. Полный startup/context, regression, integrity, backup или restore выполняются только если само изменение непосредственно затрагивает architecture boundaries, schema/migration, security/auth, data integrity, backup/restore или доказанные сквозные зависимости. Название policy/docs-задачи и найденная попутная проблема сами по себе не повышают риск-класс и не разрешают широкие проверки.

Перед стартом Strategy передаёт Result, exact Scope/resources, First check, Acceptance и Forbidden changes. До мутаций executor требует чистый `git status --short` и запускает preflight; план, скрипт, вспомогательный файл, memory/current-context/roadmap/policy sync, backup/restore и другие процедуры допустимы только когда прямо требуются типом задачи, контрактом или утверждённым scope. Один failed targeted check разрешает одну узкую correction внутри scope и один повтор; повторная ошибка или внескоупная причина — точный blocker. Standing authorization покрывает реализацию, проверки, staging и один commit до result/blocker без промежуточных подтверждений. Все owner-gates, single writer, clean Git и resource-safe parallel limits сохраняются.

Managed sandbox остаётся внешней границей платформы: репозиторий не может гарантировать Full access, отключить approval или разрешить создание `.git/index.lock`. При блокировке обычной команды executor сразу сообщает точную операцию и внешний blocker, использует штатный platform approval flow, если он доступен, и продолжает в том же thread после разрешения. Новый executor, циклы повторных попыток и вывод о неисправности Git/БД/сервера без иных свидетельств не нужны.

Strategy и engineering-задачи могут открывать любые публично доступные URL только для read-only исследования и анализа. Запрещены login или иная авторизация, отправка форм, публикации, покупки и иные расходы, изменения аккаунтов, доступов или настроек, а также скачивание либо обработка приватных клиентских данных. CRM и сайт регистрации/личного кабинета `https://mtrhit.ru/` остаются вне доступа.

Если Strategy-чат стал слишком длинным, регулярно требует сжатия, теряет детали, путает решения или заметно расходует контекст, Strategy сам предлагает переход. Перед ним он read-only сверяет, что approved memory, current context и roadmap содержат значимые утверждённые решения, планы, ограничения, незавершённые задачи и ближайшие следующие шаги. При пробеле отдельный native task-thread синхронизирует канонический контекст; после сверки Strategy подтверждает, что новый чат продолжит работу только по startup protocol, без старой переписки.

### Controlled parallel execution v1

Короткий маршрут для любого числа проектов: `Ядро старт. Проект «Название»: задача`. Router ищет только активный проект или подпроект по точному нормализованному имени и возвращает proposal branch/worktree; в новом рабочем чате эта же команда немедленно вызывает `chat-parallel-start`, который создаёт или переиспользует изолированный scope worktree и checkpoint до первого status. До точной декларации path/SQLite/shared resources writer lease не выдаётся. Это один универсальный формат, а не набор команд по проектам; router read-only и не создаёт проекты.

Переход между длинными чатами выполняется общей командой `Переход в новый чат`. Перед writer-работой `chat-workspace-prepare` создаёт или повторно использует реальный noncanonical Git worktree и branch named scope, затем проверяет clean branch/HEAD и лишь после этого сохраняет append-only checkpoint. Следующая scoped-команда в новом рабочем чате автоматически выполняет тот же prepare/resume и проверяет worktree, branch, HEAD и clean state до status, без второго запроса владельцу. Для нового параллельного рабочего чата `chat-parallel-start` запускается непосредственно по одному тексту владельца: `Ядро старт. ТГ-боты. Имя.` или `Ядро старт. Проект «Название»: задача`; он создаёт или переиспользует отдельный scope worktree и checkpoint до status и mutation. Drift, dirty state, чужая branch, legacy checkpoint или нерегистрированный путь блокируются fail-closed. Проект должен быть заранее зарегистрирован: неизвестный или неоднозначный проект не создаётся и блокируется. Старый legacy-чат закрывают как историю и запускают свежий изолированный контур. UI не создаёт новый чат и не назначает worktree вручную созданному чату.

После внешней публикации, подтверждённой владельцем или проверяемой ссылкой, редакционный executor в card указывает точные площадку, заголовок, дату и HTTPS-URL либо явное подтверждение владельца, а до завершения той же задачи записывает факт в project editorial domain. `Заверши задачу.` сверяет факт с project SQLite и проекцией панели; одного Git-коммита недостаточно. Панель читает этот факт автоматически; отдельная задача или чат для панели не нужен. Это не автоматическая публикация и не заменяет отдельное разрешение владельца на внешнее действие.

Для завершения любой активной изолированной задачи владелец пишет ровно `Заверши задачу.` в её текущем рабочем чате. Executor выполняет только текущий Result из открытой execution card: требуемые card-проверки, один commit только относящихся tracked changes, закрытие пакета и штатную последовательную интеграцию verified branch. Он сообщает commit, результат интеграции, проверки и clean status. Отсутствие работы, невалидная card, чужой dirty state, stale base, конфликт, занятый integration lease либо недостающее разрешение — точный blocker без изменения, merge или обхода. Команда не работает в Strategy и исторических read-only чатах, не распространяется на соседние scope и не разрешает внешние действия, публикации, расходы либо изменение доступов/авторизации. Параллельные контуры могут завершаться этой же командой; integration lease остаётся единым, поэтому ожидающий контур безопасно ждёт или получает blocker.

Утверждённая v1-политика заменяет прежний глобальный запрет параллельных writer-ов только в этих пределах: максимум четыре независимых writer-а, каждый в отдельном неканоническом Git worktree и branch, с объявленными base HEAD, path, SQLite и shared resources. Handoff атомарно выдаёт leases и fail-closed отклоняет missing/invalid declaration, пятый writer, общий worktree/branch, ancestor/descendant path overlap, same SQLite и shared resource. Core/policy/config/migration/dependency/shared-runtime, central control-plane, context-pack и memory/policy mutations эксклюзивны; разные project SQLite совместимы. Integration lease всегда один, а stale base или конфликт блокирует merge без force/reset/delete. Подготовка и закрытие context pack, синхронизация approved memory и интеграция выполняются последовательно. Внутри каждого change set сохраняются один named writer, одна ветка, один commit и clean Git; read-only multi-agent pilot не меняется.

## Автономные отделы

Orchestration coordinator pilot активен только для профиля `MetricHit → Редакция`. Coordinator — временная воспроизводимая read-only роль, а не автономный отдел, writer или постоянный чат. Compiler выдаёт ему только цепочку `Ядро → MetricHit → Редакция → задача`; coordinator формирует одну полную child execution card, выбирает только установленные разрешённые skills и выполняет предметную приёмку. Lifecycle `route → claim coordinator → delegate → worker evidence → domain approve/reject → sequential integration → Strategy completion` enforced штатным handoff без новой schema. Максимальная глубина — `Strategy → coordinator → worker`, до трёх read-only research/audit веток, writer внутри change set один. UI, daemon, scheduler, API, отдельная БД отдела и автономная production-редакция остаются на паузе; отсутствие `data/editorial/editorial.sqlite` ожидаемо.

## Готовность окружения

Executor переиспользует существующие project `.venv`, системный Edge/browser, dependency caches, здоровый уже запущенный сервер и owner-facing порт. Зависимости не переустанавливаются, здоровый runtime не перезапускается и порт не меняется без фактического свидетельства проблемы. Отсутствующее или сломанное окружение оформляется точным blocker либо отдельной явно утверждённой environment-задачей. Обычная задача не устанавливает ПО, не меняет Windows/global settings, не запускает persistent server и не меняет порт.

После visual work обязательны относящийся E2E и до четырёх скриншотов проверенного результата; без них UI не объявляется готовым, кроме точного browser/platform blocker. При смене порта итог указывает старый и новый порты, причину и требуемое действие владельца.
