# Operating context MetricHit OS

## Назначение

«Ядро» — самостоятельный инфраструктурный продукт и control plane. Оно связывает информацию, утверждённую память, решения, проекты, задачи, выполнение и аудит. Система не позиционируется как редакционная платформа или замена Notion/Trello. MetricHit — первый самостоятельный проект под управлением «Ядра», а не название самого ядра.

## Границы ядра

Ядро предоставляет общие возможности памяти, решений, проектов, задач, аудита и управления Strategy. В нём есть независимый проект «Развитие Ядра» для работ над самим control plane; MetricHit — первый независимый бизнес-проект, и в дальнейшем независимых проектов может быть несколько. Каждый независимый проект может иметь ровно один уровень принадлежащих только ему подпроектов. Новые задачи, рекомендации и идеи обязательно получают scope независимого проекта (по умолчанию MetricHit) и необязательного подпроекта; legacy-записи автоматически не переназначаются. Глобальная утверждённая память, решения, Strategy и audit не scoped. Текущая реализация — локальный модульный монолит на Python 3.13, FastAPI и SQLite; Node.js остаётся эталоном совместимости до отдельного решения о завершении миграции.

## Контур решений

Контур решений — часть центрального ядра, а не отдел или автономный агент. Только явно утверждённые владельцем решения могут быть approved; предложения и непринятые варианты остаются pending candidates и никогда не auto-approve. Перед сохранением проверяются semantic duplicate, evolution и conflicts. Значимые approved-решения входят в current context; технические мелкие правки решениями не считаются.

Канонический workflow engineering: `Strategy → internal native Codex task-thread/subagent → commit/result`. Strategy — основной human-language координатор продукта, архитектуры, приоритетов и разработки: до решений он сверяет approved memory, current context, operating context, roadmap и фактический Git, отмечает существенные пробелы и противоречия и предлагает ближайшие MVP-шаги. Он не требует повторять известный контекст и не считает историю чата канонической истиной. Strategy остаётся единственным постоянным видимым проектным чатом и read-only потоком: он обсуждает и анализирует, читает approved memory, Git и документы. Только после явного утверждения владельцем конкретного изменения репозитория он создаёт ровно один внутренний native Codex task-thread/subagent; сразу после запуска сообщает владельцу имя executor-а и точный scope. User-owned/sidebar-чаты и `create_thread` не используются. Planning, analysis, context reads, неутверждённые предложения и pending candidates не создают engineering-задачу. Strategy не изменяет файлы репозитория — включая memory, docs, config, code и tests — независимо от размера изменения; их изменяет только отдельный native task-thread. Инвариант: одно пользовательское engineering-решение → ровно один native task-thread. До создания Strategy проверяет, не создан ли thread для текущего пользовательского turn/решения; повторная обработка того же turn идемпотентна. Если thread уже есть, Strategy сообщает его ID и status и ничего не создаёт. Каждая новая engineering-задача требует нового native task-thread; Strategy никогда не заменяет scope существующего или завершённого thread и не переиспользует завершённый thread. Сразу после запуска task-thread сверяет свою фактическую модель с требуемой для данной задачи. Если для задачи требуется Sol или Luna, а фактическая модель иная, до любых критических действий thread останавливается и просит владельца переключить модель; после переключения он продолжает с текущего состояния, без отката, нового thread или перезапуска задачи. Пока другой engineering thread действительно выполняется, Strategy не запускает второй и не переназначает первый: он ждёт завершения либо запрашивает у владельца явную отмену. Пока executor активен, Strategy удерживает пользовательский work turn открытым и не отправляет финальный ответ о завершении; при необходимости допустим только явно помеченный in-progress комментарий. Только после commit/result и проверенного чистого `git status`, либо при реальном blocker, Strategy публикует финальный итог: готово/blocked, commit (если есть), проверки, `git status` и blocker (если есть). Периодические статусы, scheduler, UI и новая функциональность для этого не вводятся. Постоянный developer-чат не требуется. Repo-side handoff хранит решение, контекст задачи и известный итог/commit hash для audit; он не конкурирует с native task-thread как очередь исполнения. Существующие `handoff-next`, `handoff-claim` и `handoff-complete` и lifecycle `ready` → `in_progress` → `completed` остаются совместимым внутренним механизмом, но не обязательны для startup или пользовательского процесса. Dispatcher и SDK не являются обязательным контуром и не развиваются без доказанной необходимости. Постоянный контекст читается по startup protocol. UI, daemon, scheduler, OpenAI API и интеграция внутреннего API Codex не реализуются.

Если Strategy-чат стал слишком длинным, регулярно требует сжатия, теряет детали, путает решения или заметно расходует контекст, Strategy сам предлагает переход. Перед ним он read-only сверяет, что approved memory, current context и roadmap содержат значимые утверждённые решения, планы, ограничения, незавершённые задачи и ближайшие следующие шаги. При пробеле отдельный native task-thread синхронизирует канонический контекст; после сверки Strategy подтверждает, что новый чат продолжит работу только по startup protocol, без старой переписки.

## Автономные отделы

Отдел — постоянный бизнес-модуль; агент или модель — заменяемый исполнитель. Отдел может иметь собственную БД, workflow, агентов, бюджеты, расписания, согласования и аналитику. Ядро не зависит от конкретного отдела. Прямые записи между БД ядра и отделов запрещены; взаимодействие происходит через стабильные сервисные контракты.

Редакция остаётся автономным отделом и первым подключаемым модулем. Возможные будущие отделы: аналитика, продвижение, продажи, поддержка и разработка.

## Архитектурный масштаб

Сейчас используется модульный монолит. Микросервисы, Kafka и универсальная plugin-платформа не нужны. Обобщать контракты следует только после запуска минимум двух автономных отделов.

## Текущий фокус

Завершены защищённая память, рекомендации и идеи, knowledge → task, управление задачами, обзор, глобальный поиск, активность/audit, backup/restore, проекты, минимальная запись/audit для Strategy → native Codex task-thread, unified intake v1: текст, ссылки и текстовые файлы, UI управления памятью и project scope MVP. «Ядро» является самостоятельным control plane; «Развитие Ядра» и MetricHit — независимые проекты, поддерживается один уровень принадлежащих им подпроектов. Новые задачи, рекомендации и идеи scoped с default MetricHit, а legacy-записи сохранены без массового переназначения. HTML, CSS и vanilla JavaScript операторской панели выделены из серверного кода, а короткий UX-проход обзора завершён. Голос не является отдельным входящим контуром MVP: пользователь использует диктовку устройства или браузера, а в «Ядро» поступает уже текст; аудио не принимается, не транскрибируется и не хранится.

Миграция всего проекта «Ядро» на SERVER завершена и проверена. `C:\MetricHit\workspace` на SERVER — canonical primary workspace MetricHit; домашний ПК сохраняется как резервная точка и не считается primary workspace. Серверный Strategy — основной координационный чат; iPhone Remote к SERVER подтверждённо работает, а подключение ноутбука запланировано на 17.08.2026. Обычная разработка внутри `C:\MetricHit\workspace` выполняется локальным Codex в режиме Full access + Never ask, поэтому типовые действия разработки — файлы репозитория, тесты и обычный Git workflow — проходят без ручных approval prompts. Временные артефакты тестов игнорируются и не удаляются только ради чистого статуса. Этот технический режим не отменяет обязательные owner-gates из `AGENTS.md`: удаления, force-операции, изменения доступов, публикации, расходы, изменения стратегии, памяти или настроек и другие опасные действия возможны только по явному решению владельца. Managed sandbox и глобальные настройки Codex/Windows не меняются из репозитория; если они блокируют обычную команду, это внешнее техническое ограничение фиксируется без попытки обхода. Обычная разработка выполняется на GPT-5.6 Terra Medium; Sol и Luna используются только по утверждённой policy. Editorial OpenAI API, автоматические публикации и production-развитие редакции остаются на паузе.

## Model routing и память

По умолчанию используется GPT-5.6 Terra с reasoning Medium. Требуемая модель определяется отдельно для каждой задачи; специальные модели предлагаются согласно утверждённой политике и включаются только после подтверждения владельца, без переноса разрешения Sol/Luna на следующую задачу. Сразу после запуска engineering task-thread обязан сверить фактическую модель с требуемой; при несовпадении требуемой Sol/Luna он до критических действий останавливается и просит владельца переключить модель, а затем продолжает с текущего состояния без отката, нового thread или перезапуска. Перед решениями утверждённая память проверяется штатным read-only путём; она выше предположений модели. Расхождения кода, памяти и документов выясняются, а не угадываются. Semantic-дубли запрещены; запись выполняется только штатным идемпотентным workflow.
