# Operating context MetricHit OS

## Назначение

MetricHit OS — центральное операционное ядро бизнеса. Оно связывает информацию, утверждённую память, решения, проекты, задачи, выполнение и аудит. Система не позиционируется как редакционная платформа или замена Notion/Trello.

## Границы ядра

Ядро отвечает за память, проекты, задачи, решения, права, аудит, бюджеты, согласования и резервирование. Текущая реализация — локальный модульный монолит на Python 3.13, FastAPI и SQLite. Node.js остаётся эталоном совместимости до отдельного решения о завершении миграции.

## Контур решений

Контур решений — часть центрального ядра, а не отдел или автономный агент. Только явно утверждённые владельцем решения могут быть approved; предложения и непринятые варианты остаются pending candidates и никогда не auto-approve. Перед сохранением проверяются semantic duplicate, evolution и conflicts. Значимые approved-решения входят в current context; технические мелкие правки решениями не считаются.

Канонический workflow engineering: `Strategy → native Codex task-thread → commit/result`. Strategy — постоянный поток: он фиксирует явно утверждённый короткий decision/task context в repo-side handoff, запускает для каждой engineering-задачи отдельный native Codex task-thread и не меняет код. Инвариант: одно пользовательское engineering-решение → ровно один native task-thread. До создания Strategy проверяет, не создан ли thread для текущего пользовательского turn/решения; повторная обработка того же turn идемпотентна. Если thread уже есть, Strategy сообщает его ID и status и ничего не создаёт. Каждая новая engineering-задача требует нового native task-thread; Strategy никогда не заменяет scope существующего или завершённого thread и не переиспользует завершённый thread. Сразу после запуска task-thread сверяет свою фактическую модель с требуемой для данной задачи. Если для задачи требуется Sol или Luna, а фактическая модель иная, до любых критических действий thread останавливается и просит владельца переключить модель; после переключения он продолжает с текущего состояния, без отката, нового thread или перезапуска задачи. Пока другой engineering thread действительно выполняется, Strategy не запускает второй и не переназначает первый: он ждёт завершения либо запрашивает у владельца явную отмену. После commit/result и чистого `git status` предыдущий thread закрыт для новых задач. Постоянный developer-чат не требуется. Repo-side handoff хранит решение, контекст задачи и известный итог/commit hash для audit; он не конкурирует с native task-thread как очередь исполнения. Существующие `handoff-next`, `handoff-claim` и `handoff-complete` и lifecycle `ready` → `in_progress` → `completed` остаются совместимым внутренним механизмом, но не обязательны для startup или пользовательского процесса. Постоянный контекст читается по startup protocol. UI, daemon, scheduler, OpenAI API и интеграция внутреннего API Codex не реализуются.

## Автономные отделы

Отдел — постоянный бизнес-модуль; агент или модель — заменяемый исполнитель. Отдел может иметь собственную БД, workflow, агентов, бюджеты, расписания, согласования и аналитику. Ядро не зависит от конкретного отдела. Прямые записи между БД ядра и отделов запрещены; взаимодействие происходит через стабильные сервисные контракты.

Редакция остаётся автономным отделом и первым подключаемым модулем. Возможные будущие отделы: аналитика, продвижение, продажи, поддержка и разработка.

## Архитектурный масштаб

Сейчас используется модульный монолит. Микросервисы, Kafka и универсальная plugin-платформа не нужны. Обобщать контракты следует только после запуска минимум двух автономных отделов.

## Текущий фокус

Завершены защищённая память, рекомендации и идеи, knowledge → task, управление задачами, обзор, глобальный поиск, активность/audit, backup/restore, проекты и минимальная запись/audit для Strategy → native Codex task-thread. Ближайший этап — единый входящий поток текста, ссылок и файлов; голос преобразуется в текст, аудио не хранится. После него — UI управления памятью.

Серверный перенос больше не на паузе: весь проект «Ядро» будет перенесён на SERVER. Только после успешной миграции и проверок SERVER становится primary workspace; домашний ПК до подтверждения миграции остаётся резервной точкой. Сам перенос ещё не выполнен. Editorial OpenAI API, автоматические публикации и production-развитие редакции остаются на паузе.

## Model routing и память

По умолчанию используется GPT-5.6 Terra с reasoning Medium. Требуемая модель определяется отдельно для каждой задачи; специальные модели предлагаются согласно утверждённой политике и включаются только после подтверждения владельца, без переноса разрешения Sol/Luna на следующую задачу. Сразу после запуска engineering task-thread обязан сверить фактическую модель с требуемой; при несовпадении требуемой Sol/Luna он до критических действий останавливается и просит владельца переключить модель, а затем продолжает с текущего состояния без отката, нового thread или перезапуска. Перед решениями утверждённая память проверяется штатным read-only путём; она выше предположений модели. Расхождения кода, памяти и документов выясняются, а не угадываются. Semantic-дубли запрещены; запись выполняется только штатным идемпотентным workflow.
