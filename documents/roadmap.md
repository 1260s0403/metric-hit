## Следующие этапы

### Завершено — структурированная память `Ядро → проект → подпроект → задача`

Целевая архитектура утверждена 30.08.2026 и реализована 31.08.2026. `AGENTS.md` остаётся короткой конституцией Strategy; изменяемые знания живут в scoped memory. Strategy сначала определяет scope и тип задачи, затем compiler собирает минимальный context pack только из нужной родительской цепочки. Общие знания хранятся один раз на ближайшем общем уровне; sibling scope и история без основания не загружаются. Канонический контракт — `documents/structured-memory.md`, schema — migration v11, compiler/router — `scripts/structured-memory.mjs`.

1. **P0 — контракт и baseline завершены.** Зафиксированы паспорт scope, ownership, слои, актуальность, наследование, task context pack, безопасный routing audit и baseline 147 579 байт / 1,21 мс.
2. **P1 — паспорта и принадлежность завершены.** Созданы паспорта Ядра, MetricHit, «Редакции» и «Панели»; бесхозные записи fail-closed уходят в очередь и не входят в активную память.
3. **P2 — слои, актуальность и наследование завершены.** Resolver поддерживает permanent/working/historical, все утверждённые freshness statuses, `supersedes`, запрет ослабления core prohibition и изоляцию sibling scopes.
4. **P3 — router, context pack и audit завершены.** Существенная неоднозначность возвращает один вопрос; audit хранит только fingerprint и технические сигналы, а временный пакет явно закрывается.
5. **P4 — context compiler и эффективность завершены.** Сборка детерминирована, обязательные правила сохранены, история и siblings по умолчанию исключены, объём пилотного пакета меньше baseline.
6. **P5 — MVP-пилот MetricHit завершён.** «Редакция» получает Ядро + MetricHit + «Редакция», «Панель» — Ядро + MetricHit + «Панель»; sibling leakage отсутствует, команда «Проверь панель» требует уточнить scope.

Этапы выполнены строго P0 → P5; acceptance каждого предыдущего подтверждался до следующего. Дальнейшее расширение структурированной памяти требует отдельного in-scope решения владельца.

Для будущих in-scope доработок запрос владельца является постоянным разрешением на реализацию, тесты, обычный staging и один commit; повторное промежуточное подтверждение не требуется. Исключения — удаление, force-операции, внешняя публикация, расходы, изменения доступов/прав, стратегии, политики памяти, настроек/глобальной системы и существенное расширение scope. Внешние managed-sandbox prompts отменить невозможно.

Техническое разделение независимых проектов завершено на `acff1db909c9cf9b7b85f0c2a18b035f3d3fa2c0`. Любой зарегистрированный managed project маршрутизируется по canonical `project_id` в собственный `project.sqlite`; central остаётся control plane. Invalid/unknown/unregistered/missing storage отклоняются fail-closed; N-project federated/project store и memory routing работают, совместимость MetricHit сохранена. Изоляция и export/import доказаны на двух временных проектах; реальный второй проект не создавался. Следующий продуктовый шаг появляется только вместе с реальным вторым проектом либо после отдельного решения владельца о UI. Cleanup legacy-копий также требует отдельного решения. Термин «MetricHit OS» не используется для целевой модели.

Следующий editorial-этап — ещё не реализованный on-demand research-MVP: реестр надёжных источников, датированные research-находки, дедупликация и оценка релевантности к семантическому ядру и editorial-реестру, а также краткий research-brief по запросу. В этот этап не входят scheduled monitoring и автопубликация. UI редакции — отдельное будущее решение.

Маркетинговые, дизайн- и development-навыки установлены как глобальные инструкции Codex; это не меняет настройки, внешние сервисы, продуктовый код или интерфейс. Обсуждение возможного смыслового пересечения «Моих идей» и «Рекомендаций» остаётся неутверждённым и требует отдельного решения владельца.
