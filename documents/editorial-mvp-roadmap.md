# Дорожная карта редакции: активный маршрут статьи с изображениями

> Актуализация 2026-09-05. Раздел ниже заменяет активную 12-недельную automation-схему. Старый текст сохранён как исторический план и не разрешает Research-сервис, publishing или Measurement.

## Действующая граница

Редакция поставляет проверенный комплект «статья + картинки» для ручного размещения. В scope не входят индексация, позиции, ПФ и его эффективность, конверсионный Measurement, автопубликация, scheduler, monitoring, новые API-интеграции и постоянные чаты. Выбор структуры реальной статьи и любые внешние действия сохраняют owner-gates.

## Этапы и статус

| Этап | Результат | Acceptance / проверка |
|---|---|---|
| 0 | Согласованный план и handoff | docs-only `git diff --check` |
| 1 | Единый spec и обязательный фактический QA (A–D, L) | source copy не получает ложный zero-overlap; null-spec, неверные link/LSI/image refs и metadata-only visual pass блокируются; `node --test tests/editorial-contract.test.mjs tests/structured-memory.test.mjs` |
| 2 | Реальные coverage/geo/rules и утверждение структуры (E–G) | README не заменяет реестр; структура не selected до owner choice |
| 3 | Connected lifecycle и recovery (H–K) | retry/recovery/migration проверены реальным путём без дублей |
| 4 | Быстрый маршрут с безопасной параллельностью (N) | Writer один; staging и общие ресурсы изолированы и сериализованы |
| 5 | 2–3 настоящих комплекта | проверены текст, real images, timings и revisions; публикации не имитируются |

P0/P1 — история поставленных primitives, не статус полного acceptance: P0 остаётся открытым до Этапа 1, P1 — до Этапа 3; N запрещает включать параллельный production путь до Этапа 4. Следующий этап — 1.

# Историческая дорожная карта автоматизации (неактивна)

Статус документа: архитектурный план, не разрешение на разработку или подключение площадок. Горизонт — 12 недель при одном backend-разработчике полной занятости и в среднем 0.2 ставки владельца/редактора на решения и приёмку; security review привлекается в контрольных точках. При меньшем ресурсе срок пересматривается, а безопасность не сокращается. Базовый режим всех интеграций — `simulation`.

Связанные документы: [архитектура](editorial-automation-architecture.md), [модель данных](editorial-data-model.md), [ежедневный цикл](editorial-daily-workflow.md), [матрица площадок](editorial-publishing-matrix.md), [стоимость и безопасность](editorial-cost-and-safety.md), [открытые вопросы](editorial-open-questions.md).

## 1. Однозначная граница первого релиза

MVP состоит из одного детерминированного оркестратора и семи последовательных этапов: Research, Planning, Writing, Review, Approval, Publishing и Measurement. На один рабочий день он может подготовить не более одного полного материала и двух производных постов.

В первый релиз входят:

- исследование только по утверждённому allowlist с сохранением происхождения данных;
- сопоставление кандидатов с существующей семантикой и реестром публикаций;
- объяснимый план дня, включая допустимый результат «сегодня не публиковать»;
- один Markdown-материал, HTML-preview и до двух оригинально адаптированных постов;
- один личный Telegram-бот как интерфейс согласования, но не как хранилище;
- раздельное одобрение плана, текста и факта публикации;
- автоматическая публикация в Telegram только после проверки официального механизма, прав и точного подтверждения владельца;
- VK в режиме `draft-only`: MVP создаёт проверяемый payload/manual preview, но сетевой adapter и включение `automatic` остаются после MVP;
- готовые ручные пакеты для Дзена, Sostav/SBlogs, Oborot.ru, Timeweb и Workspace;
- реестр публикаций, аудит, идемпотентность, журнал стоимости и простой сбор доступных метрик;
- полный режим симуляции без изменений внешних площадок.

В MVP не входят большая веб-панель, несколько ботов, CRM и клиентские данные, изменение `mtrhit.ru`, автономное изменение стратегии или утверждённой памяти, публикация без владельца, браузерная автоматизация и сложная атрибуция эффективности.

## 3. Минимальный набор компонентов

```text
editorial-cli / scheduler
        |
        v
deterministic orchestrator ---- audit/cost ledger
        |
        +-- approved-memory reader (read-only)
        +-- editorial SQLite + work/editorial files
        +-- research adapters (allowlist, read-only)
        +-- AI gateway (budgets, schemas, model routing)
        +-- approval adapter (one Telegram bot)
        +-- publishing adapters
              |-- Telegram: conditional automatic
              |-- VK: offline draft-only package
              `-- other platforms: manual-package
```

Не нужны отдельный message broker, Kubernetes, vector database или несколько автономных агентов. Один процесс и SQLite достаточны для MVP при глобальной блокировке run, транзакционном outbox и резервном копировании. Внешний scheduler должен только запускать команду; логика времени, пропусков и повторов остаётся в оркестраторе.

## 4. Контрольные демонстрации

1. **Empty day:** источники не дают сильной темы — система предлагает `no_publish`, не вызывает Writing и не расходует основной бюджет.
2. **Full simulation:** одна тема превращается в статью и два поста, владелец возвращает версию на доработку, затем одобряет; итог — три `would_publish` и ноль внешних изменений.
3. **Crash recovery:** процесс останавливается после записи outbox и безопасно продолжается без дубля.
4. **Approval binding:** после одобрения меняется один символ — прежнее разрешение становится недействительным.
5. **Manual platform:** пакет для Sostav содержит текст, media manifest, источники и checklist, но не пытается входить на площадку.
6. **Recovery:** отдельное восстановление возвращает editorial SQLite, Markdown/preview, аудит и связь версий с публикациями.

## 5. Критерий готовности MVP

MVP считается готовым не по количеству сгенерированных текстов, а когда одновременно доказаны: корректный `no_publish`; трассировка каждого существенного утверждения; ручное согласование трёх областей; отсутствие внешних изменений в simulation; отсутствие дублей при сбоях; восстановление реестра и файлов; работа бюджетного стопа; одна проверенная Telegram-публикация в тестовом target. Перевод production-target выполняется отдельным решением владельца после завершения этой дорожной карты.
