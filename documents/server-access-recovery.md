# Аварийное восстановление доступа к серверу

Этот документ предназначен владельцу и будущему экземпляру Codex на случай, если
RDP показывает тёмный экран «Подождите», зависает сеанс или пропадает обычный
доступ к Windows-серверу. Документ не содержит паролей, приватных SSH-ключей,
токенов или резервных кодов.

## Проверенное состояние на 6 сентября 2026 года

- Сервер: Windows Server 2025 Standard, публичный адрес `65.109.62.241`.
- Административная учётная запись для удалённого входа: `root`.
- SSH: TCP-порт `22`, служба Windows OpenSSH `sshd`.
- RDP: TCP/UDP-порт `7777`, включена Network Level Authentication.
- SSH-вход по ключу проверен с iPhone и ноутбука.
- В `C:\ProgramData\ssh\administrators_authorized_keys` сохранены отдельные
  публичные ключи с комментариями `mobile@localhost` и `laptop`, а также ранее
  существовавший ключ `MetricHit-server`.
- Приватные ключи находятся только на соответствующих устройствах. Их нельзя
  копировать в репозиторий, чат или на сервер.
- Пароль учётной записи `root` в ходе настройки и аудита не изменялся.

## Быстрый вход

С ноутбука Windows:

```powershell
ssh -i "$env:USERPROFILE\.ssh\id_ed25519" root@65.109.62.241
```

С iPhone в a-Shell:

```sh
ssh -i .ssh/id_ed25519 root@65.109.62.241
```

При запросе `passphrase` вводится пароль локального приватного ключа устройства,
а не пароль Windows. Выйти из SSH без изменения сервера:

```text
exit
```

Если SSH сообщает, что ключ сервера изменился, не удалять запись из
`known_hosts` автоматически. Сначала проверить причину изменения через поставщика
сервера или из уже доверенного сеанса: неожиданная смена ключа может означать
переустановку сервера либо подмену соединения.

## Безопасная последовательность при зависшем RDP

1. Не закрывать последний работающий RDP- или SSH-сеанс до появления второго
   проверенного канала доступа.
2. Проверить SSH с iPhone или ноутбука. Если появляется приглашение вида
   `root@SERVER C:\Users\Administrator>`, аварийный доступ работает.
3. Сначала выполнить только диагностику: проверить время загрузки, службы SSH/RDP,
   слушающие порты, активные сеансы и свежие ошибки журналов.
4. Не менять пароль `root`, SSH-ключи, брандмауэр, RDP, Defender или сетевые
   настройки во время диагностики.
5. Не перезапускать `sshd`, RDP-службы или Windows, пока не подтверждён резервный
   канал доступа. Перезагрузка допускается только по прямой команде владельца.
6. После восстановления отдельно проверить, что повторный SSH-вход работает и с
   iPhone, и с ноутбука.

## Read-only диагностика для Codex

Следующие команды ничего не исправляют и не должны изменять состояние сервера:

```powershell
Get-CimInstance Win32_OperatingSystem | Select-Object LastBootUpTime
Get-Service sshd,TermService | Select-Object Name,Status,StartType
Get-NetTCPConnection -State Listen | Where-Object LocalPort -in 22,7777
quser
Get-WinEvent -FilterHashtable @{LogName='System';StartTime=(Get-Date).AddHours(-2)} -ErrorAction SilentlyContinue |
  Where-Object LevelDisplayName -in 'Ошибка','Критический','Error','Critical' |
  Select-Object -First 30 TimeCreated,Id,ProviderName,Message
```

Для проверки свежего интернет-перебора отдельно смотреть:

- Security, событие `4625` — неудачные входы Windows/RDP;
- `OpenSSH/Operational` — ошибки SSH-аутентификации;
- текущие соединения к локальным портам `22` и `7777`.

Большое число неудачных входов с разных публичных IP само по себе не доказывает
взлом: это обычное автоматическое сканирование открытых портов. Признаками,
требующими расследования, являются неизвестный успешный вход, новый пользователь
или администратор, новая служба/задача автозапуска, очистка журналов, неизвестный
процесс или изменение SSH-ключей.

## Уже выявленные риски, которые нельзя исправлять «заодно»

- SSH и RDP доступны из интернета и подвергаются автоматическому перебору.
- SSH пока допускает парольную аутентификацию.
- Блокировка учётной записи после неудачных попыток отключена.
- Некоторые PowerShell-скрипты задач, запускаемых от `SYSTEM`, доступны группе
  `Authenticated Users` на изменение.
- Аудит Windows настроен неполно; отсутствие события не гарантирует отсутствие
  действия.
- Defender работает, но Tamper Protection выключена и полное сканирование ранее
  не было зарегистрировано.

Любое исправление этих пунктов требует отдельного плана, прямого разрешения
владельца и проверки, что рабочие SSH-ключи не дадут потерять доступ.

## Запреты для будущего восстановления

- Не сохранять здесь и в других файлах пароль `root` или приватные ключи.
- Не заменять целиком `administrators_authorized_keys`; добавлять новый публичный
  ключ только идемпотентно и сохранять существующие ключи.
- Не отключать парольный SSH-вход до успешной проверки ключей с двух устройств.
- Не закрывать порт `7777` и не ограничивать IP без согласованного альтернативного
  канала доступа.
- Не считать сервер взломанным только по неудачным попыткам входа, но и не считать
  его чистым без проверки успешных входов и механизмов автозапуска.
