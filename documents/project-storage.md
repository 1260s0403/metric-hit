# Физическое хранилище проектов «Ядра»

## Контракт первого этапа

Каждый независимый проект получает отдельный SQLite-файл по детерминированному пути:

`data/projects/<project_id>/project.sqlite`

`project_id` принимается только как канонический UUID версии 4 в нижнем регистре. Значение не используется как произвольная часть пути: переходы `..`, абсолютные пути, разделители, альтернативное написание UUID и ссылки на общий каталог отклоняются до создания файлов.

В каждом новом файле хранится только служебная таблица `project_storage_metadata` с идентификатором проекта и версией формата хранилища. При повторной инициализации файл открывается только для проверки. Если его идентификатор, формат или целостность не совпадают с ожидаемыми, операция завершается явной ошибкой и файл не изменяется.

## Границы фундаментального этапа

Механизм создаёт и проверяет физическую границу проектного хранилища. Сам initializer не переносит существующие данные, не меняет схему или содержимое `data/database/metrichit.db`, не подключён к рабочему runtime и операторской панели и не реализует экспорт или импорт.

## Резервирование

Все фактически созданные хранилища под этим корнем входят в единый штатный backup
«Ядра». Каждая проектная SQLite снимается безопасным online backup, сохраняется в
том же изолированном относительном пути и фиксируется в manifest с ID проекта,
размером, SHA-256, версией формата и результатом integrity check. Restore-test
повторно проверяет путь, служебную принадлежность, хэш и целостность. Это правило
не создаёт проекты, не переносит legacy-данные и не подключает проектные базы к
рабочему runtime.

## Read-only план миграции

Перед любым переносом штатный планировщик открывает legacy SQLite только для чтения и
строит детерминированный versioned manifest без пользовательского содержимого. В нём
остаются только таблица/тип записи, стабильный ID, классификация и проверяемое основание.
Принадлежность определяется исключительно явными `project_id`, `subproject_id`, ролями
проектов и структурными связями между записями; названия и текст не используются.

Неоднозначная, конфликтующая или отсутствующая принадлежность классифицируется как
`unresolved`, а `readyToMigrate` остаётся `false`.

## Утверждённые пакеты принадлежности

После проверенной полной резервной копии 35 однозначных legacy-записей получили
принадлежность через добавляемые в конец записи аудита: 31 — MetricHit, 4 — управляющий
контур «Ядра». Утверждённые и отклонённые записи памяти не переписывались. Операция
транзакционна, идемпотентна и защищена исходным SHA-256 и хэшем dry-run manifest;
точный manifest отката хранится вместе с проверенным backup set.

Во втором проверенном пакете разобраны ровно 62 решения: 7 назначены MetricHit,
54 — управляющему контуру «Ядра». Ещё у одного решения о физическом хранилище
значение `project_id="canonical_lowercase_uuid_v4"` признано описанием формата,
а не связью с проектом; отдельная append-only запись аудита сохраняет исходное
approved-содержимое и назначает решение «Ядру». Пакет защищён точным хэшем набора
ID, исходными хэшами базы и плана, транзакцией, идемпотентностью и rollback manifest
рядом с проверенным backup set.

Финальный утверждённый этап охватил все актуальные 348 `unresolved` через точный
набор из 92 первичных записей: после одной append-only коррекции итоговая
принадлежность корней составляет 63 для управляющего контура «Ядра» и 29 для
MetricHit. Связанные source/document/version/audit/task записи наследуют
принадлежность первоисточника; ранее подтверждённая принадлежность approved memory
сохраняет приоритет над provenance-ссылкой. Две ошибочные связи подпроектов с
control plane и две записи с неизвестной ролью разрешены проверяемыми структурными
назначениями без изменения исходного содержимого.

Итоговый plan содержит 0 `unresolved` и `readyToMigrate=true`.

## Материализация MetricHit

По отдельному прямому решению владельца канонический managed project MetricHit
`00000000-0000-4000-a000-000000000102` материализован в
`data/projects/00000000-0000-4000-a000-000000000102/project.sqlite`.

Target воспроизводит точную legacy schema: 10 исходных таблиц, 1 индекс и 24
триггеров, а также служебные `project_storage_metadata` и
`project_migration_manifest`. В него вошли:

- 326 строк, принадлежащих именно каноническому MetricHit: `audit_log` 193,
  `decisions` 1, `document_versions` 10, `documents` 43,
  `memory_candidates` 38, `sources` 10, `tasks` 31;
- 4 минимальные core `sources`, необходимые для замыкания пяти provenance FK;
- 10 строк `schema_migrations`, описывающих воспроизведённую schema.

Другой managed UUID `c8a8b3d0-040a-47d6-8c2d-1974f665c219` и его четыре строки
не входят в MetricHit target. Четыре ранее утверждённые структурные коррекции
применены детерминированно только к effective `data_json` в target; исходные
legacy-строки не переписывались. Embedded manifest версии 1 фиксирует точные ID,
per-table source/target hashes, schema hash, plan/source guards, dependency closure
и backup set. Создание атомарно, повторный apply только сверяет файл и не меняет
его.

Live materialization использовала plan manifest
`66891c6d4d8b223eca051d732c1833000a839f755c8fa76a1e8542af463a2c0f` и
source SHA-256 `a5f507b6a283e5b5431a95f919470c9a094908023708fa86a2704462d3f1e5de`.
Target SHA-256 после apply и replay —
`69e0ec3841ee43568aa90685c74b30c2f05f0292110f191f36e547cbd20da08d`;
embedded manifest SHA-256 —
`d3a602b3dc0b5370bb454d5943bb75cd28fbc294f66bacb04dc6c74ec46868eb`.

Legacy SQLite остаётся рабочим источником. Runtime, reads/writes, operator panel,
export/import и cutover не переключались и остаются отдельными owner-gated
этапами.
