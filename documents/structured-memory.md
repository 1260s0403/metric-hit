# Структурированная память «Ядра»

> Актуальное решение редакции 2026-09-05: По команде «Напиши [новую] статью для [площадки] [на тему …]» редакция сразу готовит одну качественную статью с изображениями. Если тема указана владельцем, она сохраняется; иначе Planner самостоятельно выбирает тему по утверждённому ядру 302 и реестру публикаций. H1 — короткий утверждённый ВЧ-маркер, а не тема статьи: его повтор разрешён и не занимает тему. Planner+Architect составляют одну внутреннюю структуру без вывода трёх вариантов и без согласования с владельцем. Writer раскрывает тему и органично подбирает релевантные ключи; структура может уточняться внутри редакции. Новизна оценивается по смыслу и финальному source-overlap, а не совпадению H1. Проверки текста и изображений, внутренний visual review по hashes и отдельный owner-gate внешней публикации обязательны. Индексация, запуск ПФ и оценка ПФ не входят в текущую работу. E_AMBIGUOUS_TOPIC допустим только при реальном конфликте исходных данных; использованные H1 не являются blocker.

Статус: канонический контракт MVP. Иерархия: `Ядро → проект → подпроект → задача`.

## P0 — контракт и baseline

`AGENTS.md` остаётся короткой обязательной конституцией Strategy. Изменяемая память хранится в SQLite и выбирается только после определения scope и типа задачи. До внедрения компилятора обязательный startup-набор (`AGENTS.md`, current context, operating context, roadmap) занимал 147 579 байт; медиана двадцати последовательных локальных чтений — 1,21 мс. Baseline измерен 31.08.2026 на HEAD `fd772a1` и нужен только для сравнения объёма, а не как норматив производительности.

Паспорт scope содержит стабильный `id`, один `scope_kind`, родителя, короткие название и назначение, статус и компактные routing aliases. Активная запись памяти обязательно содержит ровно одного владельца-scope, `semantic_key`, слой, тип, статус актуальности, источник, `valid_from` и при наличии ссылку `supersedes`.

Слои: `permanent`, `working`, `historical`. Статусы актуальности: `active`, `superseded`, `outdated`, `needs_review`, `historical`. Активный пакет не читает историю, `needs_review` или неоднозначные записи. История включается только явным диагностическим основанием.

Приоритет правил: обязательные запреты и owner-gates из `AGENTS.md`; затем активный запрет Ядра; затем ближайшее активное правило цепочки scope; затем решения и незавершённые обязательства. Нижний scope не может ослабить запрет Ядра. `supersedes` сохраняет старую запись и исключает её из активной выборки. Общая истина хранится один раз на ближайшем общем scope.

Task context pack состоит только из `AGENTS.md`, паспортов parent chain, применимых активных правил, последних пяти применимых решений, открытых обязательств и execution card. Консультация использует уже проверенный контекст текущего scope, а точечный read-only review читает указанные файлы и необходимые прямые зависимости без writer, card или полного startup. До любой editorial, code, docs, research, UI или general-задачи с изменениями router определяет scope/type, а compiler строит card с одним `Result`, точным перечнем необходимых files/resources в `Scope`, применимыми mandatory rules, одной существующей `First check`, измеримым `Acceptance` и `Forbidden changes`. Sibling/unrelated scope, история, попутные файлы и широкие проверки не загружаются без доказанной прямой зависимости. Context pack, card и preflight остаются компактной служебной подготовкой и не могут расширить scope или превратить простую задачу в системный аудит. Неполная card отклоняется fail-closed без текста запроса и reasoning.

Для editorial scope compiler дополняет scoped chain применимыми approved `editorial_rule` из совместимого approved-memory registry и узко распознанными обязательствами владельца. Это не превращает все открытые задачи в правила: platform/content signals ограничивают выбор, superseded editorial rules исключаются, Telegram-правило не попадает в TenChat, а UI/другие task types не получают editorial requirements. Каждый новый публичный пост или статья вне Telegram fail-closed требует один не-навигационный кластер утверждённого ядра из 302 запросов либо несколько документированно смежных кластеров, основной запрос, интент, площадку и format в execution card; brand/navigation исключены, а geo-кандидат допускается только после проверки спроса. Для нескольких кластеров card обязана содержать полный список и обоснование смежности при одном пользовательском интенте. Delivery QA подтверждает те же кластер или кластеры, запросы, обоснование смежности, интент и площадку, естественное заметное размещение основного запроса (H1 статьи либо headline/opening social-поста), отсутствие keyword stuffing, единый интент и evidence спроса для geo-кандидата. Для каждого такого материала главная редакционная цель — индексация Яндекса по выбранной семантике; card дополнительно fail-closed требует только SEO-цель индексации. Свежий материал не обязан быть проиндексирован к подготовке или delivery: indexability/retrievability, URL, статус и evidence индексации не являются полями card или Delivery QA и не проверяются до публикации. После независимой фактической проверки индексации опубликованный материал может быть только кандидатом будущей отдельной ПФ-кампании. Такая допустимость не разрешает публикацию, запуск ПФ, расходы или доступ к аккаунтам: каждая реальная кампания требует отдельного решения владельца с конкретными материалом/URL, бюджетом и scope. Telegram полностью исключён из требований семантики, индексации и PF-target. Новый VK-пост дополнительно проходит VK-стандарт: 1 800–2 800 знаков основного текста без internal metadata и URL; исключения 1 200–1 799 для узкой новости/чек-листа и 3 000–4 000 для подробного практического разбора требуют QA-обоснование. QA подтверждает ключ в headline и opening, два-три естественных упоминания суммарно, один кластер либо документированно смежные кластеры при едином интенте во всех разделах, ответ в начале, полезные подзаголовки или чек-лист, конкретику, практический вывод и один естественный CTA; вода, повторы и неподтверждённые SEO-обещания отклоняются. Статья и TenChat дополнительно требуют утверждённую article policy и owner obligation о ВЧ-запросе в H1; TenChat также требует собственную политику объёма, одного интента, естественного ключа и отсутствия ссылочного спама. Mandatory card хранит не только semantic keys, но и точное содержание и approved source.

Открытый пакет является единственным основанием исполнения. Перед поставкой `close` перечитывает сохранённую card и требует результат, факт соблюдения scope, выполнение той же `First check`, подтверждение каждого acceptance-критерия и отсутствие нарушений `Forbidden changes`. При неполном или отрицательном evidence пакет остаётся `open`; только успешная проверка записывается в тот же payload и переводит пакет в `closed` с `terminal_outcome=delivered`. Невыполненный или осиротевший пакет терминализируется отдельно как `terminal_outcome=abandoned`: обязательны причина, владелец операции и append-only audit; delivery evidence не создаётся, а повтор операции является no-op. Поэтому физический `status=closed` означает терминальное состояние, а успешную поставку доказывает только `terminal_outcome=delivered`. Таким образом, подмена card между стартом и поставкой и ложное успешное закрытие не допускаются. Пакет временный: `open` во время задачи и терминальный после неё. Routing audit хранит fingerprint, совпавшие технические сигналы, выбранные scope/type и исход маршрута; текст запроса и внутреннее reasoning не сохраняются.

Для редакционного scope подтверждённая владельцем публикация или проверяемая ссылка до закрытия той же card объявляется точными площадкой, заголовком, датой и HTTPS-URL либо явным подтверждением владельца, затем записывается штатной publication-record операцией. `close` fail-closed сверяет каждый факт с published-записью и материалом в canonical project SQLite и сохраняет evidence этой проверки; это та же проекция, которую читает operator panel. Один Git-коммит без записи не является delivery. Это не создаёт отдельный panel scope, не публикует автоматически и не ослабляет owner-gate.

Прямое in-scope указание владельца `сделай`, `реализуй`, `доделай`, `исправь`, включая `делай сам`, действует непрерывно до delivery или реального технического blocker: executor сам создаёт/claim-ит внутренний handoff и integration lease, выполняет checks, один commit и последовательную integration без второй команды владельца. Отсутствие исходного handoff не blocker. Точная команда владельца `Заверши задачу.` — только запрос подготовиться к переходу в вручную созданный новый чат в активном изолированном writer scope. Если Result ещё не delivered, executor сначала автономно завершает его по исходному разрешению, затем обязательно вызывает штатный CLI `chat-finish`; только успешный `chat-finish` проверяет delivered context pack, сохраняет clean checkpoint и возвращает `copy_command`. Финальный ответ содержит ровно один отдельный fenced code block с языком text, содержащий только scoped startup-команду из `copy_command`, без иных результатов вместо неё. Старый чат не закрывается и не архивируется. Несколько независимых writer scopes могут получить эту команду одновременно, но integration выполняется строго по одной lease; ни один scope не выполняет cross-merge. Команда не применяется к Strategy или историческому read-only чату и не является разрешением на внешнее действие, публикацию, расходы, удаление или изменение авторизации/доступов.

Исполнение не выходит из объявленного вектора. Попутная проблема сохраняется только в итоговом evidence как observation/blocker и не исправляется автоматически; если она делает Result невозможным, пакет не расширяется и работа останавливается с точным blocker. Один failed targeted check допускает одну узкую correction в разрешённом Scope и один повтор; повторная ошибка или внескоупная причина блокируют delivery. Standing in-scope authorization действует до Result/blocker без повторных подтверждений, а 5/10-минутные цели ограничивают служебный контур и размер полезного этапа, но не создают confirmation loop.

Подготовка и закрытие context pack являются эксклюзивными control-plane операциями и не входят в параллельную writer-фазу. Для controlled parallel execution v1 каждый writer получает отдельный открытый пакет, неканонический worktree и ветку; handoff объявляет точные path, SQLite и shared resources. Перед mutation clean check относится к активному зарегистрированному изолированному worktree, а canonical проверяется штатно при preparation и последовательной integration. Не более четырёх writer leases могут быть активны одновременно. Пересечения path по ancestor/descendant, одна SQLite, core/policy/config/migration/dependency/shared-runtime, central DB, memory/policy/context-pack и integration ресурсы блокируются fail-closed. Разные project SQLite допускаются. Integration lease один; stale base или конфликт запрещают интеграцию без force/reset/delete.

Универсальный short router принимает `Ядро старт. Проект «Название»: задача` и резолвит только активный project/subproject по точному нормализованному имени. Его `project-task-route` остаётся read-only proposal branch/worktree и не заменяет обязательную точную resource declaration для handoff. Однако в новом рабочем чате тот же единственный текст немедленно вызывает `chat-parallel-start`: он создаёт или переиспользует отдельный managed worktree и v3 checkpoint для нормализованной пары project+task до первого status. Telegram-боты используют тот же startup activation путь через `Ядро старт. ТГ-боты. Имя.`. Неизвестный проект не создаётся; старые checkpoint без isolation contract не возобновляются.

Canonical primary workspace остаётся `C:\MetricHit\workspace`. Исполнительские директории допускаются только в зарегистрированных неканонических Git worktree этого же репозитория внутри `C:\MetricHit\worktrees`, после штатной проверки регистрации, branch, HEAD, clean state и отсутствия конфликтующего lease. Это не самостоятельные клоны, не новый primary workspace и не разрешение на другие соседние каталоги или глобальные настройки. Продолжение той же линии переиспользует подходящий чистый зарегистрированный worktree штатным workflow; новый чат или повтор начатой задачи сами по себе не основание создавать ещё одну рабочую копию. Managed sandbox и owner-gates сохраняются.

Chat continuity использует существующий append-only audit без новой schema. Перед checkpoint writer запускает repo-side `chat-workspace-prepare`: он создаёт либо повторно использует один детерминированный зарегистрированный noncanonical Git worktree и branch scope; existing нерегистрированный путь, чужая branch, dirty state или HEAD mismatch блокируются. Checkpoint v3 записывается только после Git-проверки clean worktree/branch/HEAD, а resume повторяет ту же проверку. Обе bare-команды `Ядро старт` и `Ядро старт.` читают Strategy state read-only по прямой команде владельца. Каждая scoped-команда `Ядро старт. Название.` в новом рабочем чате сначала выполняет prepare/resume и не имеет права выдавать status, пока не подтверждены отдельная branch, абсолютный registered worktree, HEAD и clean state; failure выводит blocker без fallback к канонической копии или логической `work/` папке. Telegram-боты образуют постоянное направление: `Ядро старт. ТГ-боты.` адресует общий контур, а `Ядро старт. ТГ-боты. Название.` — отдельный стабильный checkpoint конкретного бота и проходит ту же обязательную activation; старое единственное имя `ТГ-бот` служит только alias общего направления и не объединяет checkpoints конкретных ботов. История чата не копируется, prompt/reasoning не сохраняются; UI не создаёт чат и не умеет привязать вручную созданный чат к worktree.

Editorial `close` дополнительно требует структурированный content-QA report с `performed`, `passed`, точным текстовым результатом и машинно-проверяемыми полями каждого применимого check. Для TenChat это character count, один intent, ключ в H1/начале, естественность и 2–4 ссылки без spam; article policy требует ровно четыре естественные ссылки на `https://go.mtrhit.ru/` в начале, двух body positions и final/CTA. Для Oborot полноформатный минимум составляет 9 000 знаков; объём выше 9 000 принимается только с документированным QA-обоснованием числа ключей, без верхнего потолка. Originality проверяется только локальным детерминированным source-overlap report: SHA-256 материала и источников, overlap percent и отсутствие template match. Сторонние plagiarism и AI detectors не имитируются: их status может быть только `unavailable` или `not_performed` с явным пояснением. Неполный, отрицательный или приписывающий внешний результат QA оставляет пакет открытым.

## P1–P5 — проверяемая карта

- P1: `scope_passports`, обязательная ownership-ссылка записей и fail-closed `unresolved_memory_queue`; бесхозная запись не попадает в resolver.
- P2: `scoped_memory_records`, явные layer/status/source/validity/supersedes и детерминированное наследование без sibling leakage.
- P3: router, один уточняющий вопрос при существенной неоднозначности, обязательная execution card, временный context pack и безопасный audit.
- P4: повторяемый compiler из одной родительской цепочки; история и sibling scopes выключены по умолчанию; неполный preflight и неподтверждённая delivery validation блокируются; `metrics.compiled_bytes` сравнивается с baseline.
- P5: паспорта `Ядро`, `MetricHit`, `Редакция`, `Панель`. Редакционная задача получает первые три, UI-задача — `Ядро + MetricHit + Панель`; команда только со словом «панель» требует уточнения.

## On-demand ссылки на объёмную project memory

Migration v12 добавляет в central control plane компактную scoped-ссылку на утверждённое семантическое ядро MetricHit. Ссылка принадлежит цепочке `MetricHit → Редакция`, применима только к типам задач `editorial` и `research` и не содержит 302 запроса. Обычный MetricHit/UI context pack не получает ни эту ссылку, ни полный список.

Полная taxonomy открывается только явным `includeReferencedContent` для уже маршрутизированной editorial/research-задачи. Compiler читает её исключительно из `data/projects/00000000-0000-4000-a000-000000000102/project.sqlite`, проверяет служебный `project_id`, approved status, semantic key, SHA-256 содержимого и точное количество 302. Central legacy-копия сохраняется как audit/history, но не используется для раскрытия ссылки. Несовпадение project identity, hash или количества блокирует компиляцию fail-closed. Migration применяется и к project SQLite для общей schema history, но не создаёт там вторую scoped-ссылку.

Для изменения самого compiler/schema/memory workflow целевая проверка — `node --test tests/structured-memory.test.mjs`, затем `node scripts/check-memory.mjs`. Для docs-only изменения этого контракта достаточно `git diff --check`. Полная Node/Python regression, SQLite integrity, backup и restore обязательны только когда фактическое изменение непосредственно затрагивает соответствующие architecture boundaries, schema/migration, data integrity, backup/restore или доказанные сквозные зависимости; формулировка policy-задачи сама по себе этого не требует.

Owner-gates не меняются: удаление, force-операции, внешняя публикация, расходы, доступы/права, стратегия, политика памяти, глобальные/системные настройки и существенное расширение scope требуют отдельного решения владельца.

## Orchestration v1

Первый active coordinator profile — `metrichit.editorial.v1`, точный scope `MetricHit → Редакция`, task types `editorial` и `research`. Coordinator создаётся как временная read-only роль из профиля и compiler-generated context pack; постоянный чат, собственная память или произвольное чтение sibling scope ему не разрешены. Пакет обязан содержать только `Ядро → MetricHit → Редакция → задача` и применимые approved requirements.

Coordinator формирует ровно одну дочернюю execution card для одного writer-а: Result, exact scope/resources, mandatory rules, First check, measurable Acceptance и Forbidden changes. Card должна оставаться внутри parent scope и точно повторять approved resource declaration. Skills — декларативные identifiers из task-type allowlist установленных навыков; unknown/disallowed identifier, duplicate и auto-install отклоняются. Максимальная глубина — `Strategy → coordinator → worker`; worker не делегирует. До трёх read-only research/audit веток можно объявить отдельно, но они не получают mutation lease.

Handoff metadata без новой schema enforce lifecycle: `routed → coordinator_claimed → delegated → worker_in_progress → worker_submitted → domain_approved → integrating → integrated → completed`. Reject возвращает задачу в `delegated`, сохраняет submission/review audit и допускает повторную сдачу тем же незавершённым worker. Переходы, ownership и replay проверяются fail-closed. Integration начинается только после domain approval и сохраняет stale-base/conflict/single-lease правила. Strategy completion требует того же закрытого parent context pack, approved domain review, integrated commit/result и clean-delivery evidence. Prompt и reasoning в audit не сохраняются.
