# Политика выбора модели Codex

- Исходное решение: 13.08.2026; дополнено владельцем 15.08.2026, 16.08.2026, 26.08.2026 и 05.09.2026.
- Источник: прямое подтверждение владельца MetricHit.

## Модель по умолчанию

GPT-5.6 Terra с reasoning Medium рекомендована для обычного Strategy и standard executor-задач. Рекомендация относится к внутренней маршрутизации там, где платформа поддерживает выбор, и не меняет автоматически выбранную владельцем модель текущего Strategy-чата или глобальные настройки приложения.

## Переключение для специальных задач

- Luna назначается для полностью определённой механической low-risk задачи в явном scope, если не требуется архитектурный выбор или трактовка спорных требований, а результат проверяется простой целевой проверкой. Примеры: утверждённая замена текста, форматирование и извлечение или классификация по готовому правилу.
- Terra назначается, когда для обычной локальной реализации нужно самостоятельно выбрать решение внутри scope.
- Sol назначается для фактической complex architecture, security/auth, schema/data integrity, shared runtime или существенной неоднозначности. Sol является единственным writer такого этапа либо выполняет обоснованный независимый review; два writer-а не редактируют один результат.
- Перечисленные критерии являются постоянным разрешением на Luna и Sol: отдельное подтверждение на каждую новую задачу или этап не требуется. Если Luna обнаруживает неоднозначность, следующий исполнитель получает уже собранные факты и задача маршрутизируется на Terra или Sol.
- Astra применяется только после отдельного прямого решения владельца. Она не выбирается автоматически для Strategy или executor-задачи.

Нет автоматической цепочки всех моделей и нет обязательного review Terra после Luna. Один набор изменений имеет одного writer, а проверки определяются фактическим изменением, а не моделью. Внешние owner-gates, редакционные profile approvals, production pause, расходы и доступы эта политика не отменяет.

## Жизненный цикл выбора модели

- Перед каждой новой задачей Strategy классифицирует фактический риск и выбирает модель по этим критериям. Сама рекомендация не меняет текущую owner-selected модель чата.
- Если платформа позволяет выбрать модель, исполнитель сверяет фактическую модель с маршрутом до критических действий. Недоступность Luna для подходящей механической задачи переводит её на GPT-5.6 Terra с reasoning Medium без blocker. Если для этапа требуется Sol, его недоступность является техническим blocker: рискованный этап нельзя молча понизить до другой модели. Необходимая передача модели сохраняет факты, текущий diff и выполненные проверки; она не начинает работу с нуля.

## Зафиксированный план будущей доработки AGENTS.md

Этот план утверждён владельцем как план следующего этапа. Он не изменяет lifecycle, внешние gates, память или другие правила сам по себе; каждое изменение политики требует точного текста и отдельной реализации.

1. Подготовить редакцию `AGENTS.md`: отделить консультацию и точечный read-only review от исполнения; принять обе формы `Ядро старт` и `Ядро старт.` и запускать полный startup только по прямой команде владельца; явно привязать Git clean check к активному изолированному worktree; разделить запись уже утверждённого решения и изменение политики памяти. Отдельно утвердить текст для необходимых новых файлов внутри scope. Предложение для второго failed check: прекращать работу при доказанной внескоупной причине или отсутствии прогресса, а не автоматически после второго падения. Предложение для редакционного fallback: выдавать до трёх проверенных кандидатов, а при недоступном источнике указывать точный blocker, ничего не выдумывая. Resume после blocker и исправление после единственного commit остаются предложениями до отдельного решения о точном workflow. Отдельно разделить завершение результата и команду перехода в новый чат.
2. Закрепить быстрый маршрут Strategy: ответ из контекста для консультации, чтение указанного файла и необходимых зависимостей для review, компактная передача Terra для простой реализации и расширенные процедуры только для фактического повышенного риска. Повторно читать контекст лишь при смене scope, изменении правила или конкретном пробеле; каждая дополнительная проверка должна иметь причину. Не повторять достаточные проверки executor-а без противоречия или новых изменений, останавливать работу по достижении acceptance, а routine in-scope решения не эскалировать владельцу. Компактная card содержит только Result, scope, применимые rules, первую проверку, acceptance и forbidden changes; все уже выданные разрешения передаются executor-у.
3. Сверить проект редакции только с относящимися operating procedures, scoped memory и реальными workflows; разделить уточнения от изменений политики, затем поставить один согласованный change set с целевой проверкой. Уточнить, что exclusive resource-ограничения относятся к параллельной работе и не запрещают последовательную; проверить фактическую доступность модели и инструментов, а при конфликте назвать точные противоречащие инструкции. Противоречие границы устранено прямым решением владельца 05.09.2026; точная граница закреплена в AGENTS.md и решении governance, новые рабочие копии для этой коррекции не создаются.
4. Разобрать 2–3 реальные медленные задачи (вопрос, review одного файла, небольшая правка): отделить подготовку, ожидание инструментов, исполнение и проверки; определить повторные чтения, лишние проверки и повторные вопросы; зафиксировать, вызвало ли действие правило, трактовка или техническая задержка. Постоянный подробный instrumentation не создавать; проверять улучшения небольшими партиями.
5. Проверить только инструкции и skills, участвовавшие в этих задачах: убрать подтверждённые дубли и противоречия, дать каждому правилу один основной источник, разделить обязанности Strategy/coordinator/executor и проверить актуальность команд. Массовая перепись skills не входит в план.
6. При подтверждённой необходимости улучшить передачу: передавать уже принятые решения и разрешения, отличать временный сбой от blocker, перед повтором изменяющей операции проверять её предыдущий результат, разрешать безопасный ограниченный повтор, определить возобновление после blocker и исправление после commit. Отдельно оценить цену обязательной делегации малых правок, сохраняя read-only Strategy, пока нет отдельного решения об исключении.
7. Проверить изменения на сопоставимых задачах небольшими партиями: время до принятого результата, расход при доступном измерении, число инструментальных действий и повторных проверок, вмешательства владельца и переделки. Только после этого оценить, где Terra/Luna/Sol оправданы; Astra остаётся отдельным решением владельца.
8. После каждого утверждённого этапа штатно синхронизировать approved memory, current context и roadmap без semantic-дублей, отмечая реализованное и оставшееся.

## Точная редакция первого этапа — действующее правило

Подготовлено 05.09.2026 по утверждённому плану и введено в действие прямым owner next-stage решением 05.09.2026. Это изменение реализует только следующие пять пунктов.

1. Консультация использует уже проверенный контекст текущего scope. Точечный read-only review читает указанные файлы и необходимые прямые зависимости. Исполнение с изменениями проходит штатные card, executor и validation.
2. Обе bare-команды `Ядро старт` и `Ядро старт.` запускают полный read-only Strategy startup по прямой команде владельца. При обычном продолжении startup не повторяется; дополнительные чтения нужны при смене scope, изменении правила или конкретном пробеле.
3. Перед мутациями чистота Git проверяется в активном зарегистрированном изолированном worktree исполнителя. Проверка canonical workspace относится к штатной последовательной integration.
4. Сохранение уже утверждённого решения штатным идемпотентным workflow не требует повторного согласования содержания. Изменение самой политики памяти по-прежнему требует прямого решения владельца.
5. Поставка Result включает validation, один commit и последовательную integration. Команда `Заверши задачу.` отдельно подготавливает переход через `chat-finish` и возвращает только startup-команду в отдельном fenced text блоке.
