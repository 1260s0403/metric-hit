# Контур решений MetricHit OS

- Дата решения: 15.08.2026.
- Источник: прямое утверждение владельца MetricHit.
- Статус: архитектурное решение; 26.08.2026 упрощено и ускорено: Strategy — read-only human-facing router; один точный утверждённый scope передаётся одному executor-у для одного commit либо точного technical blocker. `AGENTS.md` сокращён до обязательного startup-контракта, введены явная карта быстрых проверок, автоматический совместимый model routing fast path и переиспользование здорового окружения без ослабления gates. 30.08.2026 утверждена целевая иерархия памяти `Ядро → проект → подпроект → задача`; 31.08.2026 этапы P0–P5 реализованы и проверены на пилоте MetricHit «Редакция» и «Панель».

## Место в архитектуре

Контур решений относится к центральному ядру MetricHit OS. Он не является отделом или автономным агентом.

Решения охватывают архитектуру, продукт, приоритеты, правила, бюджеты, сроки, права, ограничения и направления проектов. Технические мелкие правки решениями не считаются.

## Статусы и контроль

Запрос владельца изменить или построить в названном scope является standing authorization и считается явным утверждением для in-scope реализации, тестов, обычного staging и одного commit; повторное промежуточное подтверждение не требуется. Отдельное явное решение владельца сохраняется только для удаления, force-операций, внешней публикации, расходов, изменений доступов/прав, стратегии, политики памяти, настроек/глобальной системы и существенного расширения scope. Managed-sandbox prompts отменить невозможно; они сообщаются только при возникновении. Если approval необходим, Strategy запрашивает его в текущем чате владельца, включая работу владельца с телефона; это не обходит sandbox и не отменяет owner-gates.

- Явно утверждённое владельцем решение может сохраняться как `approved`.
- Предложения, выводы и непринятые варианты сохраняются только как `pending candidates`.
- Потенциальные решения никогда не утверждаются автоматически.
- Перед сохранением проверяются semantic duplicate, развитие существующего решения и конфликты.
- В current context включаются только значимые approved-решения.

Решение может быть связано с проектом, задачей, источником и при необходимости Git-коммитом.

## Исполнение и будущий интерфейс

Канонический workflow engineering: `Strategy → native Codex task-thread → commit/result`. Strategy — основной human-language координатор продукта, архитектуры, приоритетов и разработки. До решений он читает approved memory, current context, operating context, roadmap и фактический Git, замечает существенные пробелы и противоречия и предлагает ближайшие MVP-шаги без раздувания scope. Он не требует от владельца повторять уже известный контекст и не считает историю чата канонической истиной.

Strategy — единственный постоянный видимый проектный чат и read-only поток: он обсуждает и анализирует, читает approved memory, Git и документы. Только после явного утверждения владельцем конкретного изменения репозитория Strategy создаёт отдельный внутренний native Codex task-thread/subagent и сразу сообщает владельцу имя executor-а и точный scope. Контролируемый multi-agent pilot ограничен 2–3 независимыми read-only research/audit-ветками одной задачи: Strategy заранее задаёт каждой ветке отдельный вопрос, ветки не меняют repository, БД, memory, config или Git, а Strategy синтезирует единый результат. Они не являются engineering executor-ами и не могут вести публикации, расходы, доступы или глобальные изменения. Он никогда не создаёт user-owned/sidebar-чат и не использует `create_thread`; planning, analysis, context reads, unapproved proposals и pending candidates не создают engineering-задачу. Strategy не изменяет файлы репозитория — включая memory, docs, config, code и tests — независимо от размера изменения. Инвариант каждого mutation/code/data/config change set: один named writer/executor, один набор изменений, один commit и чистый Git. Controlled parallel execution v1 разрешает максимум два независимых writer thread только с непересекающимися resource leases в разных worktree; второй writer не блокируется автоматически, а третий или конфликт блокируется fail-closed. До создания Strategy проверяет, не связан ли с текущим пользовательским turn/решением уже созданный thread. Повторная обработка того же turn идемпотентна: если thread найден, Strategy сообщает его ID и status и ничего не создаёт. Каждая новая engineering-задача требует нового native task-thread; Strategy никогда не заменяет scope существующего или завершённого thread и не переиспользует завершённый thread. Пока executor активен, Strategy удерживает пользовательский work turn открытым и не отправляет финальный ответ о завершении; при необходимости он пишет только явно помеченный in-progress комментарий. Только после commit/result и проверенного чистого `git status`, либо при реальном blocker, Strategy публикует финальный итог: готово/blocked, commit (если есть), проверки, `git status` и blocker (если есть). Strategy не выполняет engineering; постоянный developer-чат не входит в целевой workflow.

Для небольшой изолированной и явно утверждённой правки действует fast path. Он ограничен максимум тремя изменёнными отслеживаемыми файлами и исключает новые файлы, зависимости, runtime/configuration/system-изменения, схему данных и миграции; превышение любого предела до реализации переводит задачу в стандартный этап. Strategy передаёт одному executor-у approval, точный scope/acceptance, branch/HEAD/status и релевантный контекст. До мутаций executor проверяет `git status --short`: при любом выводе сообщает точные грязные файлы и ждёт нового прямого решения владельца, не поглощая, восстанавливая, удаляя, коммитя или обходя их. Executor использует только существующие workflow, файлы и проверки; новые скрипты, файлы, задачи, абстракции и вспомогательные контуры запрещены, пока прямо не названы в acceptance. Он не расширяет и не переосмысливает scope: новая проблема становится отдельной задачей после прямого решения владельца. Поставка — только проверенный результат с чистым Git либо точный технический blocker; частичный вывод не является поставкой.

Краткая постановка задачи всегда имеет четыре пункта: **Результат** — один проверяемый итог; **Scope** — точные затрагиваемые области; **Первая проверка** — одна существующая быстрая целевая проверка затронутого модуля; **Запрещённые изменения** — что не менять. Если такая проверка неизвестна, задача стандартная и сначала в своём scope определяет существующую проверку без запуска широкой регрессии ради поиска. Формулировки «заодно» не расширяют задачу. План, отчёт, скрипт, вспомогательный файл или иной механизм допустимы только когда прямо требуются владельцем. Если существующий workflow не позволяет получить результат, executor сообщает точный blocker, а не создаёт новый процесс. Обычная UI- или кодовая правка не синхронизирует память, current context, roadmap или policy; синхронизация нужна только по прямому запросу владельца либо для действительно значимого утверждённого решения. Проверка начинается с одного целевого сценария; полная регрессия выполняется только при крупном, высокорисковом или сквозном изменении. Отсутствие промежуточного сообщения не останавливает работу: контроль ведётся по финальному сроку и фактическому состоянию рабочей копии, а короткое обновление даётся только при фактическом прогрессе или blocker.

Strategy маршрутизирует каждую утверждённую доработку по реальному риску: UI-текст, CSS и узкие исправления не считаются архитектурными сами по себе. Малое изменение — локальная UI/CSS/текстовая правка, документация, узкое исправление или синхронизация конкретного утверждённого правила: executor автоматически использует самую быструю доступную совместимую одобренную модель с fallback на Terra Medium, выполняет целевые тесты и `git diff --check`. Стандартное изменение использует Terra Medium в ограниченном scope одного модуля с точным acceptance: повторно загружать полный проектный контекст не требуется; выполняются тесты затронутого модуля и E2E при изменении UI. Крупное изменение — архитектура, SQLite-схема/миграции, security/auth, backup/restore, целостность данных или сквозной многомодульный scope: обязательны полный startup/context, применимое подтверждение специальной модели по действующей policy и полная регрессия/integrity-проверки. Полная регрессия обязательна только для крупного, высокорискового или сквозного изменения и не запускается автоматически после каждого малого изменения. Single writer/executor, один commit, чистый Git, относящийся UI E2E и все owner-gates для удалений, force-операций, доступов, публикаций, расходов, стратегии, памяти, настроек и иных опасных действий сохраняются.

Managed sandbox является внешней границей платформы: правила репозитория не могут предоставить Full access, отключить approval или обойти запрет на создание `.git/index.lock`. При таком отказе executor сразу сообщает точную заблокированную операцию и внешний blocker, использует штатный platform approval flow, если он доступен, и после разрешения продолжает в том же thread. Повторные executor-ы, циклы попыток и вывод о неисправности Git, БД или сервера без иных свидетельств не создаются.

Strategy сам сообщает владельцу о необходимости нового Strategy-чата, если текущий чат стал слишком длинным, регулярно требует сжатия, теряет важные детали, путает решения или заметно расходует контекст. Перед переходом он read-only сверяет, что approved memory, current context и roadmap фиксируют значимые утверждённые решения, планы, ограничения, незавершённые задачи и ближайшие следующие шаги. При пробеле Strategy создаёт отдельный native Codex task-thread для штатной синхронизации канонического контекста; сам он файлы не меняет. После полной сверки он кратко подтверждает владельцу, что новый Strategy-чат восстановит всё нужное через startup protocol без истории старого чата. Каждый новый Strategy-чат принимает эту роль через startup protocol.

### Controlled parallel execution v1 — утверждённая эволюция

Прежний глобальный single-writer запрет заменён ограниченным режимом: одновременно допускаются максимум два независимых writer thread, но в каждом change set остаются один named writer, отдельная неканоническая Git worktree/branch, один commit и clean Git. До claim каждая задача обязана объявить canonical/worktree, branch, base HEAD, path, SQLite и shared resources. Missing/invalid declaration, третий writer, общий worktree/branch, ancestor/descendant path overlap, same SQLite или shared resource блокируются fail-closed. Core/policy/config/migration/dependency/shared-runtime, central control-plane, context-pack и memory/policy mutations идут эксклюзивно; разные project SQLite могут работать параллельно. Интеграция использует один lease, stale base или конфликт блокируют merge без force/reset/delete. Подготовка/закрытие context pack и синхронизация approved memory сериализованы. Read-only multi-agent pilot 2–3 веток сохраняется без изменений.

### Orchestration v1 — пилот coordinator «MetricHit → Редакция»

Strategy может маршрутизировать editorial/research-задачу во временный воспроизводимый read-only coordinator profile `metrichit.editorial.v1`. Coordinator получает только compiler-generated цепочку `Ядро → MetricHit → Редакция → задача`, создаёт одну полную child execution card одному writer-у, выбирает skills декларативно только из установленного allowlist и выполняет предметную approve/reject-проверку evidence. Максимальная глубина — `Strategy → coordinator → worker`; worker не делегирует. До трёх read-only research/audit веток допустимы, но writer внутри change set один, а глобальный предел двух writer leases сохраняется.

Штатный handoff без новой schema enforce lifecycle `route → coordinator claim → delegate → worker submit → coordinator approve/reject → sequential integration → Strategy completion`. Reject возвращает задачу на повторную сдачу с сохранением audit. Completion требует закрытого исходного context pack, approved domain review, integration result и clean-delivery evidence. UI, daemon, scheduler, API, отдельная БД отдела и автономная production-редакция не входят в этот пилот.

## Целевая архитектура структурированной памяти

`AGENTS.md` остаётся короткой конституцией Strategy: роль, обязательные инварианты, запреты, owner-gates и правила назначения исполнителя. Изменяемые знания и подробный контекст не копируются в него.

Память организуется как наследуемая цепочка `Ядро → проект → подпроект → задача`. Strategy сначала определяет scope и тип задачи, затем читает короткие паспорта выбранного scope и только относящиеся блоки памяти по родительской цепочке. Память соседних проектов и подпроектов не загружается. Общие знания хранятся один раз на ближайшем общем родительском уровне и наследуются по ссылке.

Каждый проект и подпроект получает компактный паспорт: стабильный ID, назначение, текущая цель, границы ответственности, активные правила и запреты, приоритет, ближайший шаг, связи и ссылки на подробную память. Правила наследуются сверху вниз: запреты Ядра не могут быть отменены ниже; проект и подпроект только уточняют или дополняют их; task context является временным слоем.

Память разделяется на постоянную, рабочую и историческую. По умолчанию Strategy читает постоянную и короткую рабочую память; история открывается только для спора, расследования, восстановления происхождения решения или по прямому запросу. Каждая активная запись должна иметь явные `scope`, `project_id`, необязательный `subproject_id`, `memory_layer`, `type`, `status`, `source`, `valid_from` и `supersedes`. Допустимые состояния актуальности: active, superseded, outdated, needs_review и historical. Неоднозначные или бесхозные записи не входят в активный context pack и направляются на разбор.

Для задачи Strategy формирует минимальный временный context pack: требуемый результат, project/subproject IDs, релевантные факты и правила, разрешённые и запрещённые изменения, первую проверку, acceptance, последние связанные решения и незавершённые обязательства. После завершения пакет закрывается; в постоянную память попадает только значимый подтверждённый итог. Маршрутизация сохраняет технический audit: выбранные scope и тип задачи, идентификаторы прочитанных блоков, основание выбора и состав переданного пакета без раскрытия внутреннего chain-of-thought. При существенной неоднозначности Strategy задаёт один короткий вопрос владельцу.

Context compiler детерминированно собирает `AGENTS.md + паспорт проекта + паспорт подпроекта + активные правила типа задачи + последние связанные решения + незавершённые обязательства`. Он выдаёт минимальный достаточный контекст, не загружая соседние scope и историю без основания. Канонический контракт находится в `documents/structured-memory.md`, schema — migration v11, compiler/router — `scripts/structured-memory.mjs`.

## Приоритетный план внедрения

1. **P0 — контракт и измеримая база.** Зафиксировать форматы паспорта, record ownership, memory layer, актуальность, наследование, context pack и audit; снять baseline объёма/времени текущей загрузки. Acceptance: одна каноническая спецификация, явные приоритеты правил, набор тестовых команд и отсутствие противоречий с owner-gates.
2. **P1 — паспорта и обязательная принадлежность.** Ввести паспорта Ядра, MetricHit, «Редакции» и «Панели», а для новых записей — обязательные scope и ownership-поля с fail-closed очередью разбора. Acceptance: каждый тестовый объект однозначно принадлежит одному scope; запись без принадлежности не попадает в активную память; общие знания не копируются.
3. **P2 — слои, актуальность и наследование.** Реализовать постоянную/рабочую/историческую память, статусы актуальности, `supersedes` и детерминированный resolver цепочки правил. Acceptance: запрет Ядра нельзя отменить ниже; новая версия вытесняет старую без потери истории; sibling leakage отсутствует.
4. **P3 — маршрутизатор Strategy и task context pack.** Определять scope и тип задачи, обрабатывать существенную неоднозначность одним вопросом, собирать минимальный пакет и писать безопасный audit. Acceptance: пакет содержит все обязательные поля и только релевантные записи; audit объясняет маршрут без внутреннего reasoning; временный пакет закрывается после задачи.
5. **P4 — context compiler и эффективность.** Автоматизировать выбор активных блоков и родительских ссылок с детерминированным порядком и лимитами. Acceptance: повторный запрос собирает тот же пакет; история и соседние scope не читаются без основания; объём и время загрузки измеримо ниже baseline без пропуска обязательных правил.
6. **P5 — MVP-пилот MetricHit.** Проверить полный контур на подпроектах «Редакция» и «Панель». Acceptance: редакционная команда получает MetricHit + «Редакция», UI-команда — MetricHit + «Панель»; каждая получает правила Ядра, не получает память sibling; неоднозначная команда о «панели» корректно запрашивает scope; контрольные задачи проходят acceptance без ручной подстановки лишнего контекста.

Этапы выполняются строго по порядку: P1 зависит от P0, P2 от P1, P3 от P2, P4 от P3, P5 от P4. Переход к следующему этапу допускается только после его acceptance. Этот план — приоритет №1 для развития памяти «Ядра», но не является заявлением о реализованной функциональности и не отменяет прямые операционные команды владельца.

Repo-side handoff — только каноническая запись решения, контекста задачи и известного результата/commit hash для audit. Он не конкурирует с native task-thread как очередь исполнения и не требует `handoff-next`, `handoff-claim` или `handoff-complete` на startup либо в пользовательском процессе. Эти команды и lifecycle `ready` → `in_progress` → `completed` сохраняются как совместимый внутренний механизм; claim и complete остаются идемпотентными. Отдельные UI, daemon, scheduler, OpenAI API и интеграция внутреннего API Codex не реализуются.

Workflow переиспользует существующие `sources`, `documents`, `document_versions`, `memory_candidates` и `tasks`; отдельная система задач не создаётся. UI, daemon, scheduler, OpenAI API и отдельный LLM-вызов не реализуются.

## Быстрые проверки и готовое окружение

Первая проверка берётся из канонической карты в `documents/operating-context.md`: docs-only — `git diff --check`; governance/memory — целевой Node test и `check-memory`; Python — один относящийся pytest-файл; operator panel backend — `test_operator_panel.py`; UI/E2E — `test_operator_panel_e2e.py`; JavaScript — `node --check` для `operator-panel.js`. Широкая регрессия не запускается для поиска команды и сохраняется для крупного, высокорискового или сквозного изменения.

Executor переиспользует здоровые project `.venv`, system Edge/browser, dependency caches, running server и owner-facing port. Без доказанной проблемы он не переустанавливает зависимости, не перезапускает runtime и не меняет порт. Отсутствующее или сломанное окружение является точным blocker либо отдельной явно утверждённой environment-задачей; обычная задача не устанавливает ПО, не меняет Windows/global settings и не запускает persistent server.

Fast path автоматически использует самую быструю доступную совместимую одобренную модель внутреннего executor без отдельного вопроса и при недоступности переходит на Terra Medium без blocker. Стандартные задачи используют Terra Medium. Это не меняет owner-visible Strategy-модель. Sol и Luna по-прежнему требуют явного подтверждения владельца для соответствующей задачи или непрерывного этапа.

Будущий UI контура входит в управление кандидатами памяти и должен стать основой «Центра решений владельца». Это направление развития, а не реализованная функциональность.
