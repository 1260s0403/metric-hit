# Контур решений MetricHit OS

- Дата решения: 15.08.2026.
- Источник: прямое утверждение владельца MetricHit.
- Статус: архитектурное решение; 26.08.2026 упрощено: Strategy — read-only human-facing router; один точный утверждённый scope передаётся одному executor-у для одного commit либо точного технического blocker. Ненаблюдаемые промежуточные обязательства и вспомогательные контуры исключены.

## Место в архитектуре

Контур решений относится к центральному ядру MetricHit OS. Он не является отделом или автономным агентом.

Решения охватывают архитектуру, продукт, приоритеты, правила, бюджеты, сроки, права, ограничения и направления проектов. Технические мелкие правки решениями не считаются.

## Статусы и контроль

Запрос владельца изменить или построить в названном scope является standing authorization и считается явным утверждением для in-scope реализации, тестов, обычного staging и одного commit; повторное промежуточное подтверждение не требуется. Отдельное явное решение владельца сохраняется только для удаления, force-операций, внешней публикации, расходов, изменений доступов/прав, стратегии, политики памяти, настроек/глобальной системы и существенного расширения scope. Managed-sandbox prompts отменить невозможно; они сообщаются только при возникновении.

- Явно утверждённое владельцем решение может сохраняться как `approved`.
- Предложения, выводы и непринятые варианты сохраняются только как `pending candidates`.
- Потенциальные решения никогда не утверждаются автоматически.
- Перед сохранением проверяются semantic duplicate, развитие существующего решения и конфликты.
- В current context включаются только значимые approved-решения.

Решение может быть связано с проектом, задачей, источником и при необходимости Git-коммитом.

## Исполнение и будущий интерфейс

Канонический workflow engineering: `Strategy → native Codex task-thread → commit/result`. Strategy — основной human-language координатор продукта, архитектуры, приоритетов и разработки. До решений он читает approved memory, current context, operating context, roadmap и фактический Git, замечает существенные пробелы и противоречия и предлагает ближайшие MVP-шаги без раздувания scope. Он не требует от владельца повторять уже известный контекст и не считает историю чата канонической истиной.

Strategy — единственный постоянный видимый проектный чат и read-only поток: он обсуждает и анализирует, читает approved memory, Git и документы. Только после явного утверждения владельцем конкретного изменения репозитория Strategy создаёт отдельный внутренний native Codex task-thread/subagent и сразу сообщает владельцу имя executor-а и точный scope. Он никогда не создаёт user-owned/sidebar-чат и не использует `create_thread`; planning, analysis, context reads, unapproved proposals и pending candidates не создают engineering-задачу. Strategy не изменяет файлы репозитория — включая memory, docs, config, code и tests — независимо от размера изменения; их изменяет только отдельный native task-thread. Инвариант: одно пользовательское engineering-решение создаёт ровно один native task-thread. До создания Strategy проверяет, не связан ли с текущим пользовательским turn/решением уже созданный thread. Повторная обработка того же turn идемпотентна: если thread найден, Strategy сообщает его ID и status и ничего не создаёт. Каждая новая engineering-задача требует нового native task-thread; Strategy никогда не заменяет scope существующего или завершённого thread и не переиспользует завершённый thread. Пока другой engineering thread действительно выполняется, Strategy не запускает второй и не переназначает первый: он ждёт завершения либо запрашивает у владельца явную отмену. Пока executor активен, Strategy удерживает пользовательский work turn открытым и не отправляет финальный ответ о завершении; при необходимости он пишет только явно помеченный in-progress комментарий. Только после commit/result и проверенного чистого `git status`, либо при реальном blocker, Strategy публикует финальный итог: готово/blocked, commit (если есть), проверки, `git status` и blocker (если есть). Периодические статусы, scheduler, UI и новая функциональность для этого не вводятся. Strategy не выполняет engineering; постоянный developer-чат не входит в целевой workflow.

Для небольшой изолированной и явно утверждённой правки действует fast path. Strategy передаёт одному executor-у approval, точный scope/acceptance, branch/HEAD/status и релевантный контекст. Executor использует только существующие workflow, файлы и проверки; новые скрипты, файлы, задачи, абстракции и вспомогательные контуры запрещены, пока прямо не названы в acceptance. Он не расширяет и не переосмысливает scope: новая проблема становится отдельной задачей после прямого решения владельца. Поставка — только проверенный результат с чистым Git либо точный технический blocker; частичный вывод не является поставкой.

Strategy маршрутизирует каждую утверждённую доработку по реальному риску: UI-текст, CSS и узкие исправления не считаются архитектурными сами по себе. Малое изменение — локальная UI/CSS/текстовая правка, документация, узкое исправление или синхронизация конкретного утверждённого правила: один executor запускается сразу на default Terra, выполняет целевые тесты и `git diff --check`. Стандартное изменение — ограниченный scope одного модуля с точным acceptance: повторно загружать полный проектный контекст не требуется; выполняются тесты затронутого модуля и E2E при изменении UI. Крупное изменение — архитектура, SQLite-схема/миграции, security/auth, backup/restore, целостность данных или сквозной многомодульный scope: обязательны полный startup/context, применимое подтверждение специальной модели по действующей policy и полная регрессия/integrity-проверки. Полная регрессия обязательна для крупного изменения и этапной поставки, но не запускается автоматически после каждого малого изменения. Single writer/executor, один commit, чистый Git, относящийся UI E2E и все owner-gates для удалений, force-операций, доступов, публикаций, расходов, стратегии, памяти, настроек и иных опасных действий сохраняются.

Managed sandbox является внешней границей платформы: правила репозитория не могут предоставить Full access, отключить approval или обойти запрет на создание `.git/index.lock`. При таком отказе executor сразу сообщает точную заблокированную операцию и внешний blocker, использует штатный platform approval flow, если он доступен, и после разрешения продолжает в том же thread. Повторные executor-ы, циклы попыток и вывод о неисправности Git, БД или сервера без иных свидетельств не создаются.

Strategy сам сообщает владельцу о необходимости нового Strategy-чата, если текущий чат стал слишком длинным, регулярно требует сжатия, теряет важные детали, путает решения или заметно расходует контекст. Перед переходом он read-only сверяет, что approved memory, current context и roadmap фиксируют значимые утверждённые решения, планы, ограничения, незавершённые задачи и ближайшие следующие шаги. При пробеле Strategy создаёт отдельный native Codex task-thread для штатной синхронизации канонического контекста; сам он файлы не меняет. После полной сверки он кратко подтверждает владельцу, что новый Strategy-чат восстановит всё нужное через startup protocol без истории старого чата. Каждый новый Strategy-чат принимает эту роль через startup protocol.

Repo-side handoff — только каноническая запись решения, контекста задачи и известного результата/commit hash для audit. Он не конкурирует с native task-thread как очередь исполнения и не требует `handoff-next`, `handoff-claim` или `handoff-complete` на startup либо в пользовательском процессе. Эти команды и lifecycle `ready` → `in_progress` → `completed` сохраняются как совместимый внутренний механизм; claim и complete остаются идемпотентными. Отдельные UI, daemon, scheduler, OpenAI API и интеграция внутреннего API Codex не реализуются.

Workflow переиспользует существующие `sources`, `documents`, `document_versions`, `memory_candidates` и `tasks`; отдельная система задач не создаётся. UI, daemon, scheduler, OpenAI API и отдельный LLM-вызов не реализуются.

Будущий UI контура входит в управление кандидатами памяти и должен стать основой «Центра решений владельца». Это направление развития, а не реализованная функциональность.
