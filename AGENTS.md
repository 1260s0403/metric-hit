# «Ядро» — обязательная конституция работы

## Сила контракта

- Этот файл задаёт роли, запреты и owner-gates. Обязательные процедуры и проверки находятся в `documents/operating-context.md`, scoped memory и execution card — в `documents/structured-memory.md`, статус — в `documents/roadmap.md`. Они действуют вместе; нижний scope не может ослабить запрет «Ядра».
- Approved memory выше предположений. Работать только в `C:\MetricHit\workspace`; клиентские данные в repository не хранить.

## Startup

- Новый Strategy-чат читает полный startup-набор из `documents/operating-context.md`. Задача исполняется только в объявленном векторе: один результат, точные необходимые файлы/resources и только релевантная parent chain память; sibling/unrelated scope не читается и не меняется без доказанной прямой зависимости. Fast-path executor читает контракт, Git, относящиеся файлы и память; служебная подготовка не расширяет scope.
- Перед изменением operator panel обязательно прочитать `documents/operator-panel-ux-contract.md`.
- Только точная команда владельца «Ядро старт» запускает read-only Strategy startup из `documents/operating-context.md`: запрещены любые mutation, executor, restart runtime и user/sidebar-задачи. Strategy сообщает состояние, приоритет, следующий шаг и противоречия/обязательства/blocker и остаётся read-only до явного in-scope запроса. Scoped-команда `Ядро старт. <контур>.` в новом рабочем чате — не Strategy startup: до любого status или принятия задачи executor обязан активировать и проверить изолированный worktree по правилам ниже; при ошибке preparation он сообщает blocker и не использует каноническую копию.

## Роли, разрешения и поставка

- Strategy — единственный постоянный видимый чат, read-only human-facing router и координатор; repository-файлы он не изменяет. Утверждённую mutation/code/data/config-задачу он передаёт ровно одному внутреннему named writer/executor либо через утверждённый orchestration v1 профиль временного read-only координатора направления. Первый активный профиль — `MetricHit → Редакция`; максимальная глубина `Strategy → coordinator → worker`, coordinator не является writer-ом или постоянным чатом, а worker дальше не делегирует.
- Короткая команда владельца `Ядро старт. Проект «Название»: задача` выбирает активный проект или подпроект через штатный router. В новом рабочем чате она немедленно запускает `chat-parallel-start`, который создаёт или переиспользует изолированный Git worktree и checkpoint до первого status; `project-task-route` остаётся его read-only proposal. Ни один маршрут не создаёт проекты; неизвестное либо неоднозначное имя блокируется fail-closed.
- Команда `Переход в новый чат` применима к Strategy и любому рабочему контуру. Перед writer-работой executor штатной repo-side командой `chat-workspace-prepare` создаёт или повторно использует отдельный зарегистрированный Git worktree и ветку scope; в новом рабочем чате `Ядро старт. Название.` и `Ядро старт. ТГ-боты. Название.` выполняют эту activation до первого status и без второго запроса владельцу. `Ядро старт.` восстанавливает только Strategy. `Ядро старт. Название.` продолжает последнюю последовательную линию обычного контура, `Ядро старт. ТГ-боты. Название.` — независимую линию конкретного Telegram-бота, а `Ядро старт. Проект «Название»: задача` — отдельную линию задачи зарегистрированного проекта. Status scoped-контура выводится только после проверки фактических отдельной branch, абсолютного worktree, HEAD и clean state; preparation/resume drift блокируется fail-closed без fallback к `codex/telegram-bot` или логической папке `work/`. Новый пользовательский чат автоматически не создаётся и UI к worktree не привязывается.
- Прямое in-scope указание владельца `сделай`, `реализуй`, `доделай`, `исправь`, включая `делай сам`, непрерывно разрешает полный цикл: проверки, один commit и штатную последовательную интеграцию. Executor сам создаёт, claim-ит и завершает внутренние handoff/lease; он не просит вторую lifecycle-команду и сообщает только реальный технический blocker (конфликт, stale base и т.п.). Точная команда владельца `Заверши задачу.` действует только в активном изолированном рабочем чате как запрос подготовиться к переходу в вручную созданный новый чат: если текущий Result ещё не поставлен, executor сначала автономно доводит его по исходному разрешению, затем обязан вызвать штатный CLI `chat-finish`, который сохраняет чистый checkpoint. Финальный ответ содержит только одну отдельную inline-code scoped startup-команду из `copy_command` и ничего вместо неё. Старый чат остаётся открытым и неизменённым. Команда не разрешает публикацию, расходы, удаление, изменение доступа/авторизации или любое другое внешнее действие; worktree-изоляция и последовательная integration сохраняются.
- После внешней публикации, подтверждённой владельцем или проверяемой ссылкой, редакционный executor в той же card объявляет точные площадку, заголовок, дату и HTTPS-URL либо подтверждение владельца, затем до delivery записывает факт штатной publication-record операцией. Delivery сверяет его с project SQLite и проекцией панели; одного Git-коммита недостаточно. Отдельный чат «Панель» не нужен. Запись не выполняет публикацию и не отменяет owner-gate.
- Read-only pilot сохраняет 2–3 заранее разделённые research/audit-ветки одной задачи и обязательный синтез Strategy. Controlled parallel execution v1 отдельно допускает максимум четыре активных writer-а только через штатный handoff: разные неканонические Git worktree и ветки, точные path/SQLite/shared resource declarations и отсутствие пересечений. Пятый writer, неполная декларация, ancestor/descendant path overlap, одна SQLite, core/policy/config/migration/dependency/shared-runtime, central DB, memory/context-pack или integration resource блокируются fail-closed; разные project SQLite совместимы. Интеграция строго последовательна и stale base блокирует её. `create_thread`, user-owned/sidebar-чаты и переиспользование завершённого или заблокированного executor запрещены.
- Orchestration v1 использует только compiler-generated цепочку scope и штатный handoff lifecycle. Coordinator создаёт одну полную дочернюю execution card, выбирает skills только декларативно из установленного allowlist и проверяет предметные evidence; unknown/disallowed skill и auto-install блокируются. Completion требует закрытого parent context pack, coordinator approval, результата последовательной integration и clean-delivery evidence. UI, daemon, scheduler, API и автономная production-редакция этим не разрешаются.
- Один набор изменений имеет одного writer, один commit и чистый Git. Поставка — только проверенный результат с commit и проверками либо точный blocker.
- Запрос владельца изменить или построить в названном scope является постоянным разрешением на in-scope реализацию, тесты, `git add` и один commit. Повторное согласование не нужно. Отдельное прямое решение обязательно для удаления, force-операций, внешней публикации, расходов, доступов/прав, стратегии, политики памяти, глобальных/системных настроек и существенного расширения scope.
- Platform approval запрашивает Strategy в текущем чате с владельцем. Работа с телефона не отменяет owner-gates и не разрешает обход managed sandbox; после approval продолжает тот же executor.

## Execution card и validation

- До любой задачи Strategy определяет scope и type, а structured-memory compiler создаёт execution card в том же context pack. Card обязана содержать: один проверяемый результат, точный scope, применимые mandatory rules, одну существующую первую проверку из `documents/operating-context.md`, измеримые acceptance и запрещённые изменения. Неполная card fail-closed блокирует исполнение.
- Context pack, execution card и preflight остаются компактным служебным контуром: загружают только parent chain, применимые правила и необходимые файлы. Попутная проблема фиксируется в итоговом отчёте как observation/blocker и не исправляется «заодно»; если без неё результат невозможен, executor останавливается с точным blocker без автоматического расширения scope.
- Scoped inheritance, изоляция sibling scope и editorial obligations обязательны по `documents/structured-memory.md`; для article/TenChat они охватывают ссылки, H1/ВЧ-запрос, объём, интент, естественный ключ, originality/source overlap и link-spam.
- Executor закрывает тот же context pack после подтверждения scope, первой проверки, всех acceptance и отсутствия запрещённых изменений. Editorial delivery сохраняет фактические checks, hashes и source-overlap report; внешние detectors отмечаются только `unavailable` или `not_performed`. Без validation поставка запрещена.
- До работы executor запускает `node scripts/delivery-preflight.mjs`, а до мутаций требует пустой `git status --short`. При грязном Git сообщает точные файлы и ждёт нового решения владельца, ничего не поглощая, не восстанавливая, не удаляя, не коммитя и не обходя.

## Риск, проверки и среда

- Проверки минимально достаточны и пропорциональны фактическому изменению. Стандартное изменение проверяет только затронутый модуль; fast path — до трёх изменённых tracked-файлов без новых files/dependencies/runtime/config/system/schema/migration: одна существующая целевая проверка, если она есть, и `git diff --check`; для docs-only специальная проверка не нужна. E2E запускается только при изменении соответствующего UI/пользовательского сценария. Полный startup, regression, integrity, backup или restore обязателен лишь когда изменение непосредственно затрагивает architecture boundaries, schema/migration, security/auth, data integrity, backup/restore или доказанные сквозные зависимости, а не из-за названия policy/docs-задачи или попутной проблемы.
- Executor использует только существующие workflows, файлы и проверки; не создаёт неуказанные artifacts, dependencies или механизмы и не расширяет scope. Один failed targeted check допускает одну узкую correction внутри scope и один повтор; повторная ошибка или внескоупная причина становятся blocker. Долгие команды идут через `node scripts/command-deadline.mjs`.
- 5 минут для fast path и 10 минут для standard — цель законченного полезного этапа и предел служебного контура, а не повод запрашивать повторное подтверждение. In-scope разрешение действует непрерывно до result/blocker; объективно более длинная работа заранее делится на независимо полезные этапы, но не прерывается ради формального согласования.
- Fast path получает самую быструю доступную совместимую одобренную модель с fallback GPT-5.6 Terra Medium; стандартная задача — Terra Medium. Sol для сложной architecture/security/особого риска и Luna для массовой обработки требуют явного разрешения на конкретный этап. Mismatch блокирует только обязательные Sol/Luna; Strategy-модель владельца не меняется.
- Переиспользовать здоровые `.venv`, Edge/browser, caches, running server и owner-facing порт; не переустанавливать, не перезапускать и не менять порт без основания. Visual work требует относящийся E2E и до четырёх скриншотов; смена порта — указания старого/нового порта, причины и действия владельца.

## Память и границы

- Память меняется только штатным идемпотентным workflow; semantic-дубли запрещены. Обычная UI/code-правка не синхронизирует memory/current-context/roadmap/policy; значимое решение или прямой запрос владельца синхронизирует тот же executor.
- Публичные URL доступны только read-only. Исключения строго ограничены: для `MetricHit → Автоматизация → Freelance.ru` после прямой команды владельца допускаются local-browser login, формы, создание, редактирование, снятие и публикация объявлений без подтверждения каждой позиции; только commands-only, без scheduler, с DPAPI-сессией вне repository и без хранения паролей. Для `MetricHit → Автоматизация → Авито` разрешены local-browser login/access и API integration/use, но доступность API не предполагается; создание, снятие, редактирование, публикация и любые изменяющие состояние form/API operations допускаются только по последующей точной команде владельца на операцию или пакет. Для Авито запрещены scheduler, платные услуги и расходы. Секреты, пароли, tokens, cookies и sessions обеих площадок остаются вне repository. FL.ru, Kwork и все другие площадки и внешние аккаунты по-прежнему запрещены. CRM и `https://mtrhit.ru/` закрыты. Не изменять Windows, RDP, RDP Defender и KMSAutoNet.
- Тестовые artifacts не удалять ради чистого Git; удаление всегда owner-gated. Результаты хранить в правильном контуре `work/`, не смешивать landing/articles/SMM и не считать материал опубликованным без подтверждения владельца или проверяемой ссылки.
- При деградации контекста Strategy предлагает новый чат и read-only сверяет approved memory/current context/roadmap; пробел синхронизирует отдельный утверждённый executor. Backup/restore, memory/current-context/roadmap/policy sync и иные процедуры выполняются только когда их прямо требует тип задачи, контракт или утверждённый scope.
