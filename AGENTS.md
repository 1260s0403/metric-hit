# MetricHit OS — правила работы

## Обязательный startup protocol Strategy и сложных задач

Новый Strategy-чат и engineering-задача, которая не подходит под fast path ниже:

1. Прочитать `AGENTS.md`.
2. Загрузить `knowledge/approved/current-context.md`.
3. Прочитать `documents/operating-context.md`.
4. Прочитать `documents/roadmap.md`.
5. Проверить branch, HEAD и `git status --short`.
6. Штатным read-only путём извлечь только относящиеся к задаче записи памяти.
7. Только затем планировать изменения.

## Маршрутизация утверждённых изменений по риску

- После явного утверждения владельцем небольшой изолированной правки Strategy остаётся read-only и создаёт ровно одного внутреннего executor-а с точным scope и acceptance. Один набор изменений репозитория выполняет один ответственный executor и завершает одним commit.
- Strategy классифицирует каждую утверждённую доработку по реальному риску, а не считает UI-текст, CSS или узкое исправление архитектурной задачей. Обычная работа идёт на GPT-5.6 Terra Medium без отдельного подтверждения модели; действующая policy специальных Sol/Luna сохраняется.
- **Малое изменение (fast path):** локальная UI/CSS/текстовая правка, документация, узкое исправление или синхронизация конкретного утверждённого правила памяти. Один executor запускается сразу; проверки — целевые тесты и `git diff --check`.
- **Стандартное изменение:** ограниченный scope одного модуля и одного ответственного executor-а с точным acceptance. Не требуется повторно загружать полный проектный контекст; проверки — тесты затронутого модуля и E2E, если менялся UI.
- **Крупное изменение:** архитектура, SQLite-схема/миграции, security/auth, backup/restore, целостность данных или сквозной многомодульный scope. Требуются полный startup/context, применимое подтверждение специальной модели по действующей policy и полная регрессия/integrity-проверки.
- Fast path допустим только для малого изменения, если не затрагиваются архитектура, SQLite-схема или миграции, бизнес-логика, авторизация, security, backup/restore, целостность данных либо несколько связанных модулей.
- Strategy передаёт executor-у факт owner approval, точный scope/acceptance, актуальные branch/HEAD/status и ссылки на релевантные канонические файлы. Executor читает `AGENTS.md`, сверяет branch/HEAD/`git status`, читает только относящиеся к scope файлы/контракты и извлекает только относящуюся память штатным read-only CLI. Повторно загружать весь `current-context`, `operating-context` и `roadmap` не требуется, если сама правка их не меняет и не обнаружено противоречие.
- Для fast path не создаются дополнительный task/thread, repo-side handoff, плановый артефакт или отдельная запись памяти только ради исполнения. Если решение значимое и требует памяти, тот же executor применяет существующий идемпотентный memory workflow; техническая мелкая правка в память не записывается.
- Fast path прекращается и переходит к полному startup protocol при неясном scope/approval, затрагивающем scope dirty worktree, расхождении переданного HEAD/контекста, существенном противоречии или фактическом выходе задачи за перечисленные границы.
- Managed sandbox — внешняя граница платформы, которую репозиторий не может ослабить или отменить. При отказе обычной команды, включая запрет создать `.git/index.lock`, executor сразу сообщает точную заблокированную операцию и внешний blocker, использует штатный platform approval flow если он доступен и после разрешения продолжает в том же executor-е. Не создавать новый thread, не запускать циклы повторных попыток и не диагностировать такой отказ как неисправность Git/БД/сервера без иных свидетельств.
- Качество не сокращается: каждый набор repository mutations остаётся за одним executor-ом и одним commit с чистым Git; для UI сохраняется относящийся E2E, а для крупной доработки и этапной поставки обязательны полная регрессия и integrity-проверки. Полный набор не запускается автоматически после каждого малого изменения.

Strategy — основной human-language координатор продукта, архитектуры, приоритетов и разработки. До решений он читает approved memory, current context, operating context, roadmap и фактический Git; замечает существенные пробелы и противоречия и предлагает ближайшие MVP-шаги без раздувания scope. Strategy не просит владельца повторять уже известный контекст и не считает историю чата канонической истиной.

Strategy — единственный постоянный видимый проектный чат и read-only поток: он обсуждает и анализирует, читает approved memory, Git и документы. Только после явного утверждения владельцем конкретного изменения репозитория Strategy создаёт ровно одну внутреннюю native engineering-задачу/subagent; сразу после запуска он сообщает владельцу имя executor-а и точный scope. Никогда не создаёт user-owned/sidebar-чат и не использует `create_thread`. Для планирования, анализа, чтения контекста, неутверждённых предложений и pending-кандидатов engineering-задача не создаётся. Одновременно может работать только один исполнитель; пока он активен, Strategy удерживает пользовательский work turn открытым и не отправляет финальный ответ о завершении. При необходимости он может сообщать только явно помеченный in-progress комментарий. После commit/result и проверенного чистого `git status` исполнитель завершён и не переиспользуется; только тогда либо при реальном blocker Strategy публикует финальный итог: готово/blocked, commit (если есть), проверки, `git status` и blocker (если есть). Периодические статусы, scheduler, UI и новая функциональность для этого не вводятся. Strategy не изменяет файлы репозитория — включая memory, docs, config, code и tests — независимо от размера изменения; это делает только отдельный native Codex task-thread. Постоянный developer-чат не является частью целевого workflow. Repo-side handoff — каноническая запись решения, контекста задачи и известного результата/commit для audit, а не очередь исполнения и не обязательный шаг fast path. Dispatcher/SDK не являются обязательным контуром и не развиваются без доказанной необходимости. Постоянный архитектурный контекст брать из startup protocol, не копировать его в task.

Для любого утверждённого набора repository mutations действует single-writer: ровно один ответственный executor и ровно один commit. Read-only анализ без изменений commit не требует.

## Continuity Strategy-чата

- Strategy сам сообщает владельцу, когда чат стал слишком длинным, регулярно требует сжатия, теряет важные детали, путает решения или заметно расходует контекст.
- Перед переходом в новый Strategy-чат он read-only сверяет, что approved memory, current context и roadmap содержат значимые утверждённые решения, планы, ограничения, незавершённые задачи и ближайшие следующие шаги.
- Если сверка выявляет пробел, Strategy создаёт отдельную native engineering-задачу только для штатной синхронизации канонического контекста; сам ничего в репозитории не меняет.
- После полной сверки Strategy кратко подтверждает владельцу, что новый чат восстановит необходимое через startup protocol без истории старого чата. Каждый новый Strategy-чат принимает эту же роль через startup protocol.

Утверждённая память выше предположений модели. Расхождения кода, памяти и документов нужно выяснять, а не угадывать. Semantic-дубли запрещены; записи в память выполняются только штатным идемпотентным workflow.

## Начало сеанса и память

- В начале нового сеанса читать `knowledge/approved/current-context.md`.
- Для уточнения утверждённой памяти использовать `node scripts/memory-cli.mjs` в режиме чтения.
- Перед новой работой проверять `work/inbox/` на неразобранные файлы.
- Перед изменением operator panel обязательно читать `documents/operator-panel-ux-contract.md`.
- После изменения operator panel обязательно запускать E2E-критические сценарии; наличие HTML-разметки без проверки поведения не считается достаточным тестом.
- Серверное рабочее пространство `C:\MetricHit\workspace` — основная версия материалов MetricHit.
- Сохранять результаты в соответствующий контур `work/`; не смешивать лендинг, статьи и SMM.
- Не считать материал опубликованным без подтверждения владельца или проверяемой ссылки.
- После важных решений предлагать владельцу запись в память, не создавая пустых записей.
- После завершённого этапа обновлять рабочий статус и предлагать создать резервную копию.

## Выбор модели

- По умолчанию: GPT-5.6 Terra, reasoning Medium.
- Перед каждой новой задачей заново классифицировать её и выбирать модель по её текущему типу. Разрешение на Sol или Luna действует только для конкретной задачи либо явно непрерывного этапа и не переносится автоматически дальше. Если текущая модель избыточна для новой задачи, до начала работы предложить возврат на Terra.
- Сразу после запуска автоматически созданный engineering task-thread сверяет фактическую модель с требуемой для своей задачи. Если для задачи требуется Sol или Luna, а фактическая модель иная, до любых критических действий thread останавливается и просит владельца переключить модель. После переключения он продолжает с текущего состояния без отката, нового thread или перезапуска задачи.
- Для небольших изолированных UI-правок, CSS, текстов интерфейса, узких исправлений и коротких тестовых циклов предлагать GPT-5.3-Codex-Spark. Не использовать Spark для архитектуры, SQLite-схем, бизнес-логики, авторизации, security, backup/restore, миграций и больших сквозных модулей.
- Перед сложной архитектурной, security-критичной или особо ответственной задачей предложить владельцу GPT-5.6 Sol и дождаться явного подтверждения.
- Перед массовой классификацией, извлечением, обработкой большого количества однотипных материалов или фоновыми операциями предложить GPT-5.6 Luna и дождаться явного подтверждения.
- После специальной задачи предложить вернуться на GPT-5.6 Terra с reasoning Medium.
- Не менять модель самостоятельно: сначала уведомить владельца и получить подтверждение.

## MVP и скорость

- Скорость разработки критична: реализовывать минимальный законченный пользовательский сценарий, без функций и абстракций «на будущее».
- Сложность добавлять только при доказанной необходимости. Большие задачи по возможности делить на законченные вертикальные этапы примерно по 20–30 минут.
- Не делить работу так, чтобы оставить систему небезопасной, полурабочей или неконсистентной. Нельзя экономить на целостности данных, security, idempotency, критических тестах и восстановимости; недоделанное не считается MVP.

- Работать только внутри текущего Git-репозитория.
- Strategy и engineering-задачи могут использовать только read-only доступ к публичному лендингу `https://go.mtrhit.ru/` для его review и контекста разработки.
- Не обращаться к CRM, а также к сайту регистрации и личного кабинета `https://mtrhit.ru/`.
- Разрешение на публичный лендинг не даёт права на login, отправку форм, публикацию, расходы, изменение аккаунта/доступов или production-изменения; действующие явные owner-gates сохраняются.
- Не хранить клиентские данные в репозитории.
- Не изменять Windows, RDP, RDP Defender и KMSAutoNet.
- Не выполнять без явного подтверждения владельца внешние публикации, удаления, расходы, изменения стратегии, памяти, доступов или настроек.
- В trusted `C:\MetricHit\workspace` чтение и запись файлов репозитория, тесты, `git status`/`diff`/`add`/обычный `commit` после owner approval не требуют повторного проектного согласования. Это правило не гарантирует Full access и не отменяет managed sandbox: если платформа требует approval для записи или Git lock, executor сообщает blocker сразу и использует штатный platform approval flow.
- Временные артефакты тестов не очищать ради чистого `git status`: они должны быть точечно проигнорированы. Удаление любых каталогов или файлов остаётся отдельным owner-gate, если не было явно утверждено владельцем.
- Не пытаться обходить managed sandbox или менять глобальные настройки Codex/Windows: если платформа блокирует обычную команду, немедленно зафиксировать точную операцию как внешнее техническое ограничение и запросить штатное platform approval, если оно доступно.
- Перед любыми изменениями проверять `git status`.
- После изменений проводить проверку и показывать владельцу итог.
